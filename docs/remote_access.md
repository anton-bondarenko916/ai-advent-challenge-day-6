# Удалённый доступ к локальной Ollama (ТЗ ai_1_30 + LAN)

Ollama остаётся на `127.0.0.1:11434` — **наружу не открывается**
(`OLLAMA_HOST=0.0.0.0` запрещён). Приложение поддерживает три схемы —
выберите одну в панели «Удалённый доступ» (дропдаун «Схема доступа»):

| | **LAN (локальная сеть)** | **Cloudflare Tunnel** (интернет) | **Классическая** (интернет) |
|---|---|---|---|
| Домен | **не нужен** | нужен (DNS у Cloudflare) | не нужен (бесплатный DDNS-поддомен) |
| Проброс портов на роутере | **нет** | **нет** | да (443 + 80 для Certbot) |
| Сертификаты/TLS | **нет** (трафик не покидает сеть) | нет (TLS на edge CF) | Let's Encrypt (Certbot) |
| API Key | **опционально** (можно без ключа) | обязателен | обязателен |
| Веб-чат в браузере | **да** (страница chat.html по `/`) | — | — |
| DDNS-клиент | **не нужен** | не нужен | нужен (задача планировщика) |
| Доступ | только ваша сеть | весь интернет | весь интернет |
| Публичный IP | не участвует | скрыт | виден через DNS |
| Защита | rate limit; API Key по желанию | edge TLS + Nginx (ключ + лимит) | Nginx (ключ + лимит) + HTTPS |
| Особые условия | брандмауэр — только частный профиль | таймаут 100 с до первого байта (524) | ПК доступен из интернета |

Все схемы дают одинаковый минимум защиты: Nginx проверяет
`Authorization: Bearer <API Key>` (без ключа — 401) и ограничивает
частоту запросов (10 r/s, сверх — 429).

Всё, что отмечено **[UI]**, делается кнопками панели «Удалённый доступ»
во вкладке «Настройки» (схема, API Key, генерация nginx.conf). Настройки
хранятся глобально в таблице `app_state` (ключ `ollama_remote_access`)
и переживают перезапуск.

# Схема LAN: доступ с других устройств домашней сети (без домена)

Самый простой вариант: Nginx слушает `0.0.0.0:8080` по HTTP, Ollama
остаётся закрытой на `127.0.0.1`. Трафик не покидает вашу сеть —
сертификаты и домен не нужны. Два режима:

* **С API Key** (по умолчанию): клиенты обязаны присылать заголовок
  `Authorization: Bearer` — защита от гостей Wi-Fi;
* **Без API Key** (свитч «Требовать API Key» выключен): ничего вводить
  не нужно, а по адресу `/` открывается **страница веб-чата** — сценарий
  «ввёл IP в браузере телефона и общаюсь». rate limit остаётся.

## Что сделать [UI] (на ПК с Ollama)

1. Вкладка «Настройки» → панель «Удалённый доступ» → «Схема доступа» =
   **«Локальная сеть (LAN, без домена)»** (поля DDNS и сертификатов
   заблокируются — они не нужны).
2. Для чата без ключа: выключите свитч **«Требовать API Key»**
   (поля ключа скроются). Для режима с ключом — пропустите этот шаг.
3. При необходимости поменяйте «Порт Nginx» (по умолчанию 8080).
4. Нажмите «🌐 Сгенерировать nginx.conf» — появятся два файла:
   `output\remote_access\nginx.conf` и `output\remote_access\chat.html`
   (страница чата; Nginx отдаёт её по `/`).

## Что сделать на ПК (один раз)

5. Установите Nginx для Windows: скачайте zip с
   https://nginx.org/en/download.html и распакуйте в `C:\nginx`.
6. Скопируйте сгенерированный конфиг: `output\remote_access\nginx.conf`
   → `C:\nginx\conf\nginx.conf` (с заменой).
7. Запустите Nginx:
   ```cmd
   cd C:\nginx
   start nginx
   ```
   (после смены конфига — `nginx -s reload`, проверка — `nginx -t`;
   остановка — `nginx -s stop`).
8. Узнайте IP компьютера: `ipconfig` → строка «IPv4-адрес»
   (например, `192.168.1.50`). **Закрепите** этот IP в DHCP роутера
   (статический lease), иначе он однажды сменится.
9. Откройте порт в брандмауэре Windows **только для частных сетей**:
   ```cmd
   netsh advfirewall firewall add rule name="Ollama Nginx (LAN)" ^
     dir=in action=allow protocol=TCP localport=8080 profile=private,domain
   ```
   Профиль `private` важен: в чужой/общедоступной сети порт останется
   закрытым автоматически.

## Проверка и подключение с другого устройства

10. Откройте в браузере телефона (той же Wi-Fi-сети):
    `http://192.168.1.50:8080/` — откроется **страница чата**:
    выберите модель, пишите сообщения, ответ стримится. История живёт
    только в открытой вкладке. Если сервер работает С ключом, страница
    сама спросит его при первом запросе и запомнит (localStorage).
11. Проверка API из консоли любого устройства той же сети:
    ```cmd
    curl http://192.168.1.50:8080/api/tags -H "Authorization: Bearer ВАШ_КЛЮЧ"
    REM → JSON со списком моделей (в режиме без ключа заголовок не нужен)
    curl http://192.168.1.50:8080/api/tags
    REM → {"error": "Unauthorized"} (401) — только в режиме с ключом
    ```
12. Подключение клиента (ноутбук, другой ПК, приложение):
    * Base URL: `http://192.168.1.50:8080/v1` (OpenAI-совместимый)
      или `http://192.168.1.50:8080` (нативный API Ollama);
    * заголовок `Authorization: Bearer ВАШ_КЛЮЧ` — только в режиме
      с ключом.

**Важно про само приложение**: панель «Удалённый доступ» на ПК с
Ollama — это настройка СЕРВЕРА (что и как публиковать). Само приложение
продолжает ходить на `localhost` напрямую, если поля «URL прокси» у
него пустые — так и оставьте. URL + ключ нужны только клиентам с
других устройств.

**Автозапуск после ребута**: `schtasks /Create /TN "Nginx" /SC ONSTART
/TR "C:\nginx\nginx.exe" /RU SYSTEM` (или ярлык в папке автозагрузки).

# Схема Cloudflare Tunnel (доступ из интернета, рекомендованная)

`cloudflared` — демон, который сам держит исходящее соединение с edge-
сетью Cloudflare и публикует локальный Nginx на вашем домене. Роутер не
трогается вообще, IP не публикуется, за CGNAT работает тоже.
Понадобится домен, добавленный в Cloudflare (бесплатного поддомена CF
не даёт: аккаунт бесплатен, домен — свой).

## Установка и создание туннеля

```cmd
winget install Cloudflare.cloudflared
cloudflared tunnel login
cloudflared tunnel create myai
cloudflared tunnel route dns myai ai.example.com
```

Конфиг `%USERPROFILE%\.cloudflared\config.yml`:

```yaml
tunnel: <TUNNEL-ID>
credentials-file: C:\Users\<вы>\.cloudflared\<TUNNEL-ID>.json
ingress:
  - hostname: ai.example.com
    service: http://127.0.0.1:8080
  - service: http_status:404
```

**Важно**: `service` указывает на порт Nginx из поля «Порт Nginx»
панели **[UI]** (по умолчанию 8080), НЕ на 11434 — иначе туннель
опубликует Ollama без API Key и rate limiting.

## Nginx

1. Скачайте Nginx: https://nginx.org/en/download.html → `C:\nginx`.
2. **[UI]** Схема «Cloudflare Tunnel»: заполните «URL прокси» =
   `https://ai.example.com`, сгенерируйте API Key, нажмите
   «🌐 Сгенерировать nginx.conf». В туннельном режиме конфиг — без TLS:
   `listen 127.0.0.1:8080`, наружу Nginx не смотрит, до него долетает
   только локальный cloudflared. Rate limit считается по настоящему IP
   клиента (`CF-Connecting-IP`, подделать через туннель нельзя).
3. Положите конфиг в `C:\nginx\conf\nginx.conf`;
   `start nginx` / `nginx -s reload`.

## Запуск туннеля как службы

```cmd
cloudflared tunnel run myai      REM проверить в консоли
cloudflared service install      REM служба Windows: автозапуск
```

**Ограничение бесплатного тарифа CF**: 100 секунд до первого байта
(ошибка 524). Стриминг токенов после начала ответа под него не
попадает, но холодная загрузка большой модели + очень длинный промпт
теоретически могут не уложиться. Лечение — «прогреть» модель коротким
запросом (`ollama run qwen2.5:7b "привет"`) или держать `keep_alive`.

# Классическая схема (DDNS + проброс портов)

## A.1. Бесплатный DDNS-домен

| Сервис | Домен | Особенности |
|---|---|---|
| DuckDNS | `ваш-проект.duckdns.org` | Бесплатно, токен в кабинете, простое API |
| ApertoDNS | `ваш-проект.apertodns.com` | Бесплатные поддомены, API с Bearer-ключом |
| No-IP | `ваш-проект.ddns.net` | Бесплатно, подтверждение раз в 30 дней |

**[UI]** Заполните блок «DDNS»: провайдер, домен, токен; кнопка
«🔄 Обновить IP сейчас» проверяет связку («IP обновлён»).

### DDNS-клиент на ПК (постоянное обновление)

Готовый клиент — `src/ddns_client.py`. Одноразовое обновление:

```cmd
python -m src.ddns_client --provider duckdns --domain myai.duckdns.org --token XXXX --run-once
```

Постоянная работа — задача планировщика Windows (запуск каждые 5 минут;
рабочая папка — корень проекта):

```cmd
schtasks /Create /TN "DDNS Update" /SC MINUTE /MO 5 /TR ^
  "cmd /c cd /d C:\AI\AI_2_1\deepseek-chat-app && python -m src.ddns_client --provider duckdns --domain myai.duckdns.org --token XXXX --run-once"
```

Проверка записи: `nslookup myai.duckdns.org` — адрес должен совпасть с
«Мой IP» из кабинета роутера.

## A.2. Nginx

1. Скачайте Nginx: https://nginx.org/en/download.html → `C:\nginx`.
2. **[UI]** Схема «Классическая»: заполните DDNS-домен, сгенерируйте
   API Key, нажмите «🌐 Сгенерировать nginx.conf» — конфиг с HTTPS
   появится в `output/remote_access/nginx.conf` (пути сертификатов
   подставятся автоматически: `C:/Certbot/live/<домен>/…`).
3. `C:\nginx\conf\nginx.conf` ← конфиг; `start nginx` / `nginx -s reload`.

Конфиг: `limit_req_zone rate=10r/s` + `burst=20 nodelay` (сверх — 429),
проверка Bearer-ключа (без него 401), `proxy_pass` на
`127.0.0.1:11434`, `proxy_buffering off` + таймауты 300 с (стриминг
не рвётся).

Ключ отдельно (если нужно): `openssl rand -hex 16` или PowerShell
`-join ((1..32) | ForEach-Object { '{0:x2}' -f (Get-Random -Max 256) })`.

## A.3. HTTPS

**Let's Encrypt (рекомендуется)** — Certbot для Windows:
https://certbot.eff.org/instructions?ws=other&os=windows

```cmd
certbot certonly --standalone -d myai.duckdns.org
```

Перед выпуском: 80-й порт проброшен на ПК (A.4), Nginx на время
`--standalone` остановлен. Сертификаты — `C:\Certbot\live\<домен>\`;
продление Certbot ставит в планировщик сам.

**Самоподписанный (быстрая альтернатива)**:

```cmd
openssl req -x509 -newkey rsa:2048 -nodes -days 365 ^
  -keyout privkey.pem -out fullchain.pem -subj "/CN=myai.duckdns.org"
```

Браузер будет предупреждать; пути укажите в полях **[UI]** и
перегенерируйте конфиг.

## A.4. Проброс портов на роутере

| Внешний порт | Внутренний IP | Внутренний порт |
|---|---|---|
| 443 | 192.168.1.X (IP вашего ПК) | 443 |
| 80 | 192.168.1.X | 80 (для Certbot) |

Закрепите IP ПК в DHCP (статический lease). Открытые порты означают,
что ПК доступен из интернета — защита (Nginx + API Key + rate limit +
HTTPS) обязательна, не отключайте её.

# Приёмочные проверки (чек-лист ТЗ)

| # | Проверка | Ожидание |
|---|---|---|
| 1 | `http://localhost:11434/api/tags` локально | 200, JSON моделей |
| 2 | `<адрес Nginx>/api/tags` с ключом (`Authorization: Bearer`) | 200, JSON моделей |
| 3 | То же без ключа | 401 |
| 4 | 20+ быстрых запросов подряд | HTTP 429 после лимита |
| 5 | Чат через прокси | Ответ стримится без обрывов |
| 6 | Смена публичного IP | Tunnel/LAN: ничего; классика: DDNS-клиент обновляет домен |
| 7 | `https://<домен>` | Сертификат валиден (классика: Let's Encrypt; Tunnel: автоматический CF; LAN: не применимо) |
| 8 | Телефон через мобильный интернет | Доступ работает (Tunnel/классика); в LAN — только по VPN/в своей сети |
| 9 | Ребут ПК | Службы (cloudflared, Nginx) поднялись сами |

Быстрая проверка из консоли:

```cmd
curl -H "Authorization: Bearer ВАШ_КЛЮЧ" http://<адрес-Nginx>/api/tags
curl http://<адрес-Nginx>/api/tags        REM ожидание: 401
```

# Чего НЕ делать

* ❌ Не открывать Ollama напрямую (`OLLAMA_HOST=0.0.0.0`) — только
  через Nginx.
* ❌ В схеме LAN не пробрасывать порт 8080 (или какой выбрали) на
  роутере — тогда он станет доступен всему интернету; HTTP без TLS
  рассчитан только на вашу сеть, а в режиме без API Key — тем более:
  без проброса и в частном профиле брандмауэра доступ будет только у
  вашей сети.
* ❌ В схеме LAN не менять профиль сети ПК на «Общедоступную» с
  открытым правилом — брандмауэр должен пускать порт только в частном
  профиле.
* ❌ Не публиковать туннель прямо на `http://127.0.0.1:11434` в обход
  Nginx — останетесь без API Key и rate limiting (единственная защита).
* ❌ Не использовать HTTP без шифрования для доступа ИЗ интернета
  (Tunnel шифрует на edge, классика — Let's Encrypt; LAN — исключение,
  трафик не покидает сеть).
* ❌ Не отключать rate limiting — иначе ПК завалят запросами.
* ❌ Не хардкодить API Key и не придумывать его вручную — только
  генерация (`secrets.token_hex(16)` / `openssl rand -hex 16`).
* ❌ Не забывать про стриминг (`proxy_buffering off` в конфиге).
