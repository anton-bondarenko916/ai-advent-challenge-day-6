# Filesystem MCP + agentic loop (ai_1_35)

Агент умеет работать с файлами проекта обычным текстом: «Найди все
места, где используется класс DeepSeekAgent», «Сгенерируй ADR о
выборе Ollama». LLM сама решает, какие файловые операции выполнить
(agentic loop ядра), каждый шаг виден под ответом в панели
«🛠 Инструменты».

## Компоненты

| Компонент | Файл | Что делает |
|---|---|---|
| FS MCP-сервер | `fs_server.py` | FastMCP, Streamable HTTP, порт 8005; 7 инструментов |
| Лаунчер | `src/fs_launcher.py` | Автозапуск в отдельном окне вместе с приложением |
| Регистрация в ядре | `src/agent.py` (fs_client) + `src/agent_factory.py` | tools → LLM, tool_calls → HTTP, маршрутизация по имени |
| Лог шагов | `app/ui/components.py` (`tools_panel`) | «Шаг N: 🔍 инструмент {аргументы} → результат (обрезан)», скролл при длинном логе (высота ≤ 340) |
| Сводка в сообщении | `app/ui/components.py` (`fs_summary_controls`) | Результаты поиска и созданные файлы — прямо в тексте ответа |

Инструменты: `read_file`, `read_multiple_files` (до 20 файлов),
`write_file` (создаёт каталоги), `search_files` (glob),
`search_within_files` (поиск по содержимому: файл/строка/текст),
`list_directory`, `tree` (JSON-дерево).

## Схема (оба сценария ТЗ)

```
Пользователь: Найди все места, где используется DeepSeekAgent
  → обычный ход чата → agentic loop ядра
  → LLM: search_within_files(substring="DeepSeekAgent")   [шаг 1]
  → LLM: read_multiple_files([...])                        [шаг 2]
  → финальный ответ + панель шагов под ним

Пользователь: Сгенерируй ADR …
  → LLM: list_directory → read_file (шаблон) → write_file  [шаги 1–3]
  → файл создан на диске, ответ с путём
```

Отдельного режима/команды нет: файловые инструменты доступны в
каждом ходе чата наравне с reminder/news/geo/weather/crm.

## Безопасность

- **ALLOWED_ROOT** — доступ только внутри корня (по умолчанию сам
  проект; переопределяется `FS_ROOT`/`--root`). Проверка через
  `relative_to`: обход «..», абсолютные пути наружу и «соседние»
  каталоги с похожим префиксом (`project` vs `project-evil`)
  блокируются — ошибка уходит LLM как `{"error": …}`.
- Служебные каталоги (`venv`, `.git`, `__pycache__`, `node_modules`, …)
  в поиске и дереве пропускаются.
- Защита контекста LLM: `read_file` обрезает файлы (60 000 символов),
  `search_within_files` не сканирует файлы > 1 МБ и ограничен
  `max_results` (по умолчанию 100).
- Хост только `127.0.0.1` (FS_SERVER_HOST валидируется в config).

## Защита бюджета контекста

Файловые результаты уходят в контекст LLM — их размер ограничен на
стороне сервера: `search_within_files` по умолчанию 30 записей со
сниппетом ≤120 символов, `read_file` обрезает файл на 24 000 символов.
Прецедент: 5 поисков × 100 вхождений + чтение больших файлов дали
запрос 325K символов; thinking-модель тратила бюджет `max_tokens`
(1000) на reasoning, раунды возвращали `finish_reason=length` с пустым
контентом, цикл крутился (7 одинаковых write_file), финальный ответ
был пуст. Защита в ядре (`_send_completion_with_tools`):

- ходы с инструментами получают минимум **4000** max_tokens
  (пользовательский лимит задан для обычных ответов);
- обрезанный ответ с tool_calls НЕ исполняется — один ретрай с
  удвоенным бюджетом (до 16000), при повторной обрезке цикл
  останавливается;
- пустой финальный ответ заменяется честной подсказкой (проверьте
  max_tokens в Настройках) вместо «(пустой ответ)».

## Надёжность создания файлов

Правила работы с инструментами в системном промпте (`_TOOL_USAGE_RULES`
в `src/agent.py`) перечисляют все fs-инструменты и явные сценарии,
включая: «сгенерируй/создай файл …» = собрать информацию →
**ОБЯЗАТЕЛЬНО** `write_file` (ответ без записи = задание не выполнено).
Без этого правила модель могла ограничиться поиском и ответить текстом
в чате, не создав файл (прецедент: «Сгенерируй servers.md …» → только
поиск *.md).

## Сводка в самом сообщении

Ключевые результаты файловых операций дублируются в тело ответа (шаги
остаются в сворачиваемой панели со скроллом):

- **Поиск**: «🔍 Поиск «DeepSeekAgent» (в src): найдено 3 вхождения в
  2 файлах» + список `файл:строка — фрагмент` (до 8 записей, дальше —
  «ещё N», полный список в шагах);
- **Создание**: «✍️ Создан файл: C:\…\docs\adr\0002.md» — полный путь,
  куда реально сохранился файл; кроме того путь извлекается ядром
  (`_extract_saved_file_path` понимает и write_file) — под ответом
  появляется кнопка «📂 Открыть файл».

Ошибки инструментов в сводку не попадают (они видны в логе шагов),
не-fs инструменты (погода, напоминания…) сводку не создают.

## Agentic loop

- Один общий цикл ядра «LLM → tool_calls → результат → LLM»
  (`src/agent.py`), лимит — `REMINDER_TOOLCALL_MAX_ROUNDS`,
  **по умолчанию 10** (ТЗ ai_1_35; раньше было 5).
- Если лимит исчерпан, а LLM всё ещё просит инструменты — вместо
  пустого ответа: «Достигнут лимит итераций инструментов (10)…».
- Недоступный fs-сервер не ломает диалог: tools не попадают в запрос,
  ход идёт обычным ответом (self-healing: клиент поднимает сервер
  через `restart_hook` и повторяет вызов).

## Настройки (.env)

| Переменная | По умолчанию | Описание |
|---|---|---|
| `FS_ENABLED` | `true` | файловые инструменты и автозапуск |
| `FS_SERVER_HOST` | `127.0.0.1` | адрес привязки |
| `FS_SERVER_PORT` | `8005` | порт MCP-эндпоинта |
| `FS_ROOT` | корень проекта | разрешённая директория сервера |
| `REMINDER_TOOLCALL_MAX_ROUNDS` | `10` | лимит итераций agentic loop |

## Запуск вручную

```bash
python fs_server.py --port 8005                # корень = папка скрипта
python fs_server.py --root C:/projects/demo    # свой разрешённый корень
```
