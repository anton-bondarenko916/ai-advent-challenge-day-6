# ПРОМПТ ДЛЯ CODE ASSISTANT: УПРАВЛЕНИЕ КОНТЕКСТОМ (SUMMARY) В DEEPSEEK CHAT

## ЦЕЛЬ ЗАДАЧИ
Доработать приложение **DeepSeek Chat** (Python 3.9+ / Tkinter / DeepSeek API,
с персистентностью в SQLite и подсчётом токенов) — добавить **управление
контекстом через суммаризацию**:

- последние **N** сообщений диалога отправляются в модель «как есть»;
- всё, что старше, заменяется **summary** (конспектом), который хранится
  **отдельно** и подставляется в запрос вместо полной истории;
- summary обновляется **инкрементально** каждые **K** новых сообщений.

Изменять существующие файлы **на месте**, не переписывать проект; не ломать
текущий функционал (персистентность, подсчёт токенов, mock-режим, «Повторить»,
вставку в поле ввода) и существующие тесты.

## ИСХОДНОЕ СОСТОЯНИЕ ПРОЕКТА (учесть, не ломать)
```

├── main.py            # конфиг → ContextStore → счётчик токенов/цены → DeepSeekAgent → ChatApplication
├── src/
│   ├── config.py      # DEFAULTS + _coerce; PROJECT_ROOT; get_prices()
│   ├── agent.py       # DeepSeekAgent: RLock, _message_history, _build_request(),
│   │                  # send_message(), _handle_response(), _trim_history(),
│   │                  # персист (_persist → ContextStore.save_state),
│   │                  # учёт токенов (_update_token_stats, get_token_stats)
│   ├── storage.py     # ContextStore (sqlite3): таблицы messages + meta(JSON:
│   │                  # params, stats, schema_version="1"); save_state(messages, params, stats=None)
│   ├── tokens.py      # TokenCounter: TiktokenCounter/HeuristicCounter, count_text/count_messages
│   ├── ui.py          # ChatApplication: чат, панель параметров (блок «Токены»), поле ввода,
│   │                  # статус-бар, worker-поток + queue, _on_result/_on_send_clicked
│   └── utils.py       # валидаторы, format_tokens, get_logger, humanize_api_error
├── scripts/

└── tests/             # 83 теста: agent, utils, persistence, tokens, ui_input, benchmark
```
Ключевые факты:
- `_build_request()` возвращает `{"model", "messages": list(self._message_history),
  "temperature", "max_tokens"}` — в API уходит **вся** история (system + диалог);
- `_trim_history()` ограничивает историю `max_history_messages` (по умолчанию 50),
  **молча удаляя** самые старые сообщения;
- `send_message()`: добавил user → снимок `request_messages` → `_call_api()` →
  добавил assistant → `_trim_history()` → `_update_token_stats()` → `_persist()`;
  ошибки возвращаются словарём `{"error": ...}` без исключений;
- `tokens` в результате: `prompt_tokens/completion_tokens/total_tokens` (API),
  `estimated`, `context_tokens`, `session_total_tokens`, `cost_usd`, `cache_*`;
- статистика сессии хранится в `meta['stats']` (JSON), контекст (история+параметры) —
  в таблице `messages` + `meta['params']`; `_load_context()` восстанавливает всё
  при старте **вне** mock-режима; `clear_history()` и смена system-промпта чистят
  память и диск;
- `get_token_stats()` отдаёт `{request, response, context:{tokens,messages,estimated},
  session:{...}, counter}` — этим пользуется UI (блок «Токены», статус-бар);
- среда: **нет доступа к PyPI**, из кода — нет сети; тесты офлайн (mock-агент или
  `unittest.mock` для `_call_api`); Windows + песочница: системный TEMP и удаление
  каталогов могут быть запрещены (тестовые файлы — внутри репозитория, `tests/tmp*/`).

## РЕШЕНИЯ, СОГЛАСОВАННЫЕ С ЗАКАЗЧИКОМ (реализовать именно так)
1. **Summary делает сама модель** — отдельным служебным запросом к DeepSeek API
   (тот же клиент, отдельный system-промпт-инструкция; см. п. 2).
2. **Триггер — только по числу сообщений:** сжатие выполняется, когда объём
   непокрытых «лишних» сообщений достигает **K** (`SUMMARY_EVERY_N`, по умолчанию 10).
3. **Обновление инкрементальное:** `new_summary = сжать(старое summary + новый блок)`.
4. **Подстановка в запрос — отдельным system-сообщением** сразу после основного
   system-промпта: `[system] → [system: «Краткое содержание предыдущего диалога: …»] → [последние N сообщений]`.
5. **Синхронно** внутри `send_message()` (перед сборкой запроса) — раз в K
   сообщений запрос чуть медленнее, зато поведение предсказуемо.
6. **UI:** в статус-баре — сводка о контексте; отдельное окно **«Контекст»**
   с текстом summary и кнопками «Обновить» / «Очистить» / «Закрыть».
7. **При ошибке сжатия ничего не удаляем:** диалог отправляется как есть (или с
   аварийным ограничением, см. п. 3.4), ошибка видна в статусе, сжатие
   повторяется при следующем триггере.
8. **Токены служебных запросов учитываются отдельно:** `summary_requests`,
   `summary_prompt_tokens`, `summary_completion_tokens`, `summary_cost_usd` —
   не смешиваются со статистикой диалога.

## ТРЕБОВАНИЯ К РЕАЛИЗАЦИИ

### 1. Новый модуль `src/summarizer.py`
Инкапсулирует всё, что связано с конспектом (агент лишь вызывает его):

- **Константа-маркер** `SUMMARY_MARKER = "[[СЖАТИЕ_ИСТОРИИ]]"` — обязательно
  присутствует в тексте служебного запроса. Нужна, чтобы:
  - тесты и `scripts/dialog_benchmark.py` (sim-режим) могли отличить служебный
    запрос от обычного;
  - логи/отладка были однозначны. Маркер **не должен** попадать в обычные запросы.
- **Промпт-инструкция** (шаблон, переопределяемый через конфиг): требует
  сохранить факты (имена, предпочтения, договорённости, числа, даты, ограничения,
  открытые вопросы), не выдумывать нового, писать на языке диалога, оформлять
  разделами («Факты», «Решения», «Открытые вопросы»), уложиться в лимит.
- **Класс `ContextSummarizer`** (имя на усмотрение):
  - `should_summarize(dialog, covered, keep_last, every_n) -> bool` — чистая
    функция условия срабатывания (легко тестировать);
  - `build_request(previous_summary, chunk) -> dict` — формирует служебный запрос
    (`messages` с инструкцией + маркером, `temperature`, `max_tokens`);
  - `summarize(previous_summary, chunk, call_api) -> dict` — вызывает переданный
    `call_api` (callable без сети в тестах) и возвращает
    `{"text", "prompt_tokens", "completion_tokens", "estimated", "error"}`;
  - `truncate(text, max_tokens, counter)` — обрезка конспекта по лимиту
    `SUMMARY_MAX_TOKENS` с помощью `src/tokens.py` (с пометкой в логе);
  - ошибки **не пробрасывать**: возвращать `error`, чтобы агент сохранил историю.

### 2. `src/agent.py` — управление контекстом
- **Новые параметры `__init__`**: `summarizer=None` (по умолчанию создаётся),
  `summary_settings: Optional[Dict[str, Any]] = None` (значения из конфига).
- **Внутреннее состояние** (под существующим RLock):
  - `_summary: Optional[Dict[str, Any]]` = `{"text", "covered", "updated_at",
    "model", "prompt_tokens", "completion_tokens"}`;
  - `covered` — сколько сообщений диалога (с начала, без system) покрыто конспектом;
  - служебные счётчики в `_session_stats`: `summary_requests`,
    `summary_prompt_tokens`, `summary_completion_tokens`, `summary_cost_usd`;
  - `_last_summary_error: Optional[str]` (для статуса в UI).
- **Формирование запроса** — переписать `_build_request()` (или добавить
  `_build_context_messages()` и вызывать её из `_build_request`):
  ```
  messages = [system-промпт]
  if summary есть и непустой:
      messages.append({"role": "system",
                       "content": f"Краткое содержание предыдущего диалога:\n{summary_text}"})
  messages += dialog[covered:]          # последние N «как есть» + ещё не сжатый хвост
  ```
  Инвариант: после сжатия в запрос уходят ровно `summary + последние N`
  (несжатый хвост < K, поэтому фактический размер ограничен `N + K - 1`
  сообщениями). **Полная история при этом не теряется** — она остаётся в памяти
  и в SQLite (источник правды для UI и повторного сжатия).
- **Триггер и сжатие в `send_message()`** (синхронно, до `_call_api()`):
  1. снимок диалога; `overflow = len(dialog) - N - covered`;
  2. если `SUMMARY_ENABLED` и `overflow >= K` и не mock-режим — вызвать
     `summarizer.summarize(previous_summary, dialog[covered:len(dialog)-N])`;
  3. при успехе: записать новый `_summary` (`covered = len(dialog) - N`,
     `updated_at`, токены), учесть служебные токены/стоимость в отдельных
     счётчиках, сохранить в хранилище; в лог — INFO;
  4. при ошибке: **ничего не менять** (старый summary и `covered` остаются),
     записать `_last_summary_error`, WARNING в лог, продолжить обычную отправку;
     повторная попытка — при следующем триггере.
- **Служебный запрос не должен рекурсивно сжиматься** и не попадает в
  `_message_history`/`_session_stats` диалога (только отдельные счётчики).
- **Аварийное ограничение**: если сжатие недоступно/падает, а «сырая» история
  слишком велика, применяется жёсткий предел `MAX_HISTORY_MESSAGES` (существующий,
  по умолчанию 50) — тогда в запрос уходят `summary + последние
  MAX_HISTORY_MESSAGES`, с WARNING в лог. Молчаливое удаление непокрытых
  сообщений из памяти/БД запрещено.
- **Совместимость со старым `_trim_history()`**: ограничение теперь применяется
  только к «сырой» истории как страховка (см. выше) и **никогда** не должно
  выкидывать непокрытые summary сообщения, если лимит не превышен.
- **Публичное API для UI/тестов**:
  - `get_summary() -> dict` (`{"text", "covered", "updated_at", "tokens",
    "active", "error"}`);
  - `summarize_now(force: bool = False) -> dict` — принудительное сжатие
    (для кнопки «Обновить»); `force=True` сжимает всё, кроме последних N;
    возвращает `{"updated", "covered", "error"}`;
  - `clear_summary()` — очищает конспект в памяти и в хранилище (история
    диалога не трогается);
  - расширить `get_token_stats()`:
    - `context`: добавить `messages_raw`, `messages_sent`, `summary_tokens`,
      `summary_covered`, `summary_active`;
    - `session`: служебные счётчики `summary_*`;
    - отдельный блок `summary`: `{"active", "covered", "tokens", "updated_at", "error"}`;
  - расширить результат `send_message()` (обратносовместимо, старые ключи не
    менять): в `tokens` добавить `context_messages`, `summary_covered`,
    `summarized_this_turn` (bool).
- **`clear_history()`** и **смена system-промпта** дополнительно очищают
  конспект и `covered` (в памяти и на диске). `close()` сохраняет конспект.
- **mock-режим**: сжатие не выполняется (mock не имеет реальной модели),
  конспект не создаётся; при этом mock по-прежнему не пишет и не читает хранилище.

### 3. `src/storage.py` — отдельное хранение конспекта
- Новый ключ в `meta`: `summary` (JSON: `text`, `covered`, `updated_at`, `model`,
  `prompt_tokens`, `completion_tokens`).
- `save_state(messages, params, stats=None, summary=None)`: если `summary`
  передан — записать; если `None` — **не затирать** существующий (обратная
  совместимость вызовов и тестов).
- `load_state()` возвращает дополнительно `"summary": {...}` или `None`.
- `clear()` удаляет и `summary`.
- **Без изменения структуры таблиц** и без ломающей миграции: старые БД
  (schema_version="1" без `summary`) читаются — конспекта нет, сжатие начнётся
  с нуля. Битый JSON в `summary` → предупреждение и «конспекта нет».
- Валидация при загрузке: если `covered > числа сообщений диалога` или `text`
  пуст — конспект игнорируется (с предупреждением).

### 4. `src/config.py`, `.env`, `.env.example` — настройки
Добавить в `DEFAULTS` (с корректным приведением типов, bool/float/int):
- `SUMMARY_ENABLED` (bool, **true**);
- `SUMMARY_KEEP_LAST_N` (int, **10**) — сколько последних сообщений идут «как есть»;
- `SUMMARY_EVERY_N` (int, **10**) — размер блока сжатия (K);
- `SUMMARY_MAX_TOKENS` (int, **400**) — лимит длины конспекта;
- `SUMMARY_TEMPERATURE` (float, **0.2**);
- `SUMMARY_MODEL` (str, **""**) — пусто = использовать текущую модель диалога;
- `SUMMARY_PROMPT` (str, **""**) — пользовательский промпт-инструкция вместо встроенной;
- (опционально) `SUMMARY_TIMEOUT` (float, 60.0).
- Валидация значений в агенте/суммаризаторе: `1 <= SUMMARY_KEEP_LAST_N`,
  `1 <= SUMMARY_EVERY_N <= 200`, `50 <= SUMMARY_MAX_TOKENS <= 4000`; при
  некорректных значениях — использовать значения по умолчанию и записать WARNING.
- Задокументировать переменные в `.env.example` и `.env` (в `.env` — рабочие
  значения, ничего не выдумывать как факт про цены).

### 7. Тесты (офлайн, без сети)
Новый файл `tests/test_summarization.py` (unittest; временные файлы — внутри
репозитория, `tests/tmp_summary/`):
- `should_summarize()`: границы (ровно K, меньше, больше), влияние N/covered;
- сборка запроса: после сжатия в `_build_request()["messages"]` идут
  `[system-промпт, system-summary, …последние N]`, а покрытые сообщения
  **отсутствуют** дословно; до сжатия — присутствуют все;
- инкрементальность: при втором сжатии в служебном запросе есть и старое

- счётчики: `summary_requests/summary_prompt_tokens/summary_completion_tokens/

  выставлен только в нужном ходе;
- персистентность: после «перезапуска» (новый агент на том же файле БД) конспект
  и `covered` восстановлены, повторного сжатия на старте нет;
- ошибка сжатия: `_call_api` для служебного запроса бросает ошибку → история и
  `covered` не меняются, `get_summary()["error"]` заполнен, следующий триггер
  повторяет попытку;
- `clear_summary()`, `clear_history()`, смена system-промпта очищают конспект и
  на диске;
- `SUMMARY_ENABLED=false` → сжатия нет, поведение как раньше;
- mock-режим: конспект не создаётся, БД не создаётся;
- старая БД без ключа `summary` читается корректно;
- лёгкий GUI-тест (пропускается без дисплея): окно «Контекст» открывается,
  показывает текст конспекта, «Очистить» очищает, кнопки не ломают UI.
- **Все 83 существующих теста должны остаться зелёными** (в т.ч.
  `test_persistence.py`, `test_tokens.py`, `test_ui_input.py`,
  `test_benchmark_script.py`).

## ОГРАНИЧЕНИЯ СРЕДЫ РАЗРАБОТКИ
- **Нет доступа к PyPI** — пакеты не устанавливаются; код и тесты работают на stdlib.
- **Нет сети из кода** — тесты подменяют `_call_api`/`summarizer.summarize`;
  ручная проверка с реальным API выполняется только у пользователя.

  тестовые файлы внутри репозитория (`tests/tmp*/`, шаблон уже в `.gitignore`).
