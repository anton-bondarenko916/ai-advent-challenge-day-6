# DeepSeek Chat 🧠💬

Десктопное чат-приложение на **Python** для общения с AI-агентом на базе
**DeepSeek API** с двумя интерфейсами: классический **Tkinter**
(`python main.py`) и **Flet** с RAG-пайплайном (`python app/main.py`).
Демонстрирует чистую архитектуру: инкапсулированный агент
(`DeepSeekAgent`) отделён от интерфейса, вся конфигурация — в `.env`.

## Возможности

- ✅ Чат с сообщениями, разделёнными по ролям (цвета, выравнивание, время)
- ✅ Инкапсулированный агент с историей диалога (до 50 сообщений)
- ✅ Настройки «на лету»: модель, температура, max tokens
- ✅ Смена системного промпта с подтверждением и сбросом истории
- ✅ Фоновые запросы (UI не «зависает»), статус-бар, кнопка «Повторить» при ошибке
- ✅ Отправка по кнопке или `Ctrl+Enter`, многострочный ввод
- ✅ Надёжное поле ввода: вставка любых объёмов (`Ctrl+V` / меню по правой
  кнопке), авто-высота, подсказка не мешает повторному вводу
- ✅ **Сохранение контекста между запусками** (SQLite): история и параметры
  восстанавливаются при перезапуске, диалог продолжается с того же места
- ✅ **Подсчёт токенов**: запрос, ответ, контекст истории, сумма за сессию
  (точные значения API + локальная оценка) и оценка стоимости в USD
- ✅ **Управление контекстом (3 стратегии + переключатель)**: `sliding_window`
  (последние N сообщений), `sticky_facts` (блок фактов «ключ → значение» +
  последние N), `branching` (checkpoint и независимые ветки диалога)
- ✅ **Ветки диалога**: checkpoint, две ветки от одного места, переключение,
  переименование и удаление; у каждой ветки своя стратегия и свои факты
- ✅ **Явная модель памяти из трёх слоёв** (`short_term` / `working` /
  `long_term`): кнопки сохранения у каждого сообщения, окно «Память…»,
  закрепление сообщений (pin), рабочая память задачи (своя у каждой ветки) и
  долговременная память в отдельном файле — с предпросмотром «Что уходит в
  запрос» и предложениями LLM (pending), которые применяет только пользователь
- ✅ **Mock-режим** для тестирования без API-ключа
- ✅ **Задачи как конечный автомат (FSM)**: задача задаётся сообщением
  `/задача …` в чате; план → шаги → проверка; пользователь управляет только
  переходами между этапами (план и итог), шаги выполняются автоматически;
  пауза/продолжение/остановка с любого этапа, панель задачи над чатом,
  восстановление активной задачи после перезапуска (состояние в SQLite);
  **явная матрица переходов**: единый контроллер `TaskFSM.transition_to`
  проверяет допустимость (LLM предлагает — код решает), все попытки
  (успешные и отклонённые) пишутся в журнал `task_events`, лимит откатов
  валидации `TASKS_MAX_RETRIES`, граф состояний на Canvas в панели задачи
  с подсветкой текущей стадии
- ✅ **Инварианты — жёсткие правила проекта**: глобальные и профильные,
  категориями с приоритетами; агент учитывает их в каждом ответе, отказывается
  нарушать (даже по прямому запросу в чате) и предлагает альтернативы;
  пост-проверка ответа вторым LLM-вызовом с автоперегенерацией (лимит из
  конфига) и логом нарушений; вкладка «Инварианты» и кнопка «📋 Инварианты»
  в панели задачи
- ✅ **MCP-клиент и панель инструментов**: подключение к MCP-серверу
  по stdio через официальный Python SDK `mcp` (по умолчанию —
  open-internet-mcp: 26 открытых API без ключей — `wikipedia_summary`,
  `github_search`, `arxiv_search`, `open_meteo_forecast`, `usgs_quakes`…);
  панель рядом с чатом показывает статус, список инструментов (имя,
  описание) и inputSchema каждого (модальное окно с JSON по клику);
  кнопка «Обновить» запрашивает список в фоновом потоке (UI не блокируется),
  ошибки подключения показываются в статусе и messagebox, сворачивание
  панели сохраняется в SQLite
- ✅ **MCP-сервер «Smart Reminder» (HTTP + tool calling + SSE)**:
  собственный сервер напоминаний `reminder_server.py` на Streamable HTTP
  (`http://127.0.0.1:8000/mcp`, stateful), SQLite и APScheduler внутри
  (проверка due-напоминаний каждую минуту); LLM сама распознаёт просьбу
  «напомни … через N минут» и вызывает `add_reminder` (tool calling:
  tools напоминаний передаются в DeepSeek, `tool_calls` выполняются
  HTTP MCP-клиентом, результат возвращается модели для финального ответа);
  сработавшие напоминания приходят в чат как SSE-уведомления —
  «🔔 Напоминание: …»; сервер запускается приложением в отдельном окне
  консоли, живёт 24/7 (не перезапускается, если уже работает, и не
  останавливается при закрытии приложения); индикатор состояния и кнопка
  «🔔 Перезапустить сервер» — в верхней панели
- ✅ **MCP-сервер «News» и agentic loop** (новости → сводка → файл):
  LLM сама строит цепочку `search_news` (RSS: lenta.ru/rssexport.rbc.ru
  + запасная, feedparser, недоступные ленты пропускаются) →
  `summarize_text` (собственный вызов DeepSeek внутри news-сервера,
  при ошибке — fallback на сырой текст) → `save_to_file`
  (`output/news_YYYYMMDD_HHMMSS.md`); результат каждого шага возвращается
  модели для решения о следующем, лимит циклов — 5; по сохранённому файлу
  в чате появляется кнопка «📂 Открыть файл» (`os.startfile`)
- ✅ **Цепочка MCP-серверов «гео → погода»**: два собственных сервера —
  `geo_server.py` (`get_user_city`: город по IP через ip-api.com) и
  `weather_server.py` (`get_weather`: Open-Meteo, геокодинг + прогноз);
  на вопрос «Какая сегодня погода?» LLM сама вызывает `get_user_city`,
  получает город и передаёт его в `get_weather` — вызовы маршрутизируются
  на разные серверы по имени инструмента; панель MCP показывает все
  серверы группами с их инструментами и вызывает инструмент на своём
  сервере
- ✅ **Удалённый доступ к Ollama через Nginx** (ai_1_30): три схемы — классическая (DDNS + проброс портов + HTTPS), Cloudflare Tunnel (без DDNS и проброса) и локальная сеть (HTTP, API Key опционален, веб-чат chat.html по `/`); API Key + rate limit + генерация nginx.conf из UI
- ✅ **Telegram-бот для локальной модели** (ai_1_31): `python telegram_bot.py` — long polling (порты наружу не открываются), белый список Telegram ID, раздельная история диалогов в SQLite, команды /start /help /clear /model, ответы из Ollama из любой точки мира
- ✅ **AI-ревью PR: watcher GitHub + RAG по коду + Inspectra**: `python run_pr_watcher.py` — polling GitHub API каждые 5 минут, RAG по `*.py` проекта (коллекция `project_code` в Chroma), ревью локальной моделью `qwen2.5-coder-14b-32k` (Modelfile, num_ctx 32768) через `inspectra review --post-comment --pr-summary`, промпт с фокусом «баги и edge cases», повторное ревью по новому head_sha
- ✅ Встроенные офлайн-тесты (`unittest`)

## Установка и запуск

Требуется **Python 3.9+**.

```bash
# 1. Клонируйте/скопируйте проект и перейдите в его каталог
cd deepseek-chat-app

# 2. (Рекомендуется) создайте виртуальное окружение
python -m venv .venv
# Windows: .venv\Scripts\activate      Linux/macOS: source .venv/bin/activate

# 3. Установите зависимости
pip install -r requirements.txt

# 4. Создайте файл .env из образца и впишите API-ключ
#    Windows:  copy .env.example .env
#    Linux/macOS: cp .env.example .env
#    Затем откройте .env и укажите:  DEEPSEEK_API_KEY=sk-...
#    (ключ можно получить на https://platform.deepseek.com)

# 5. Запуск
python main.py
```

### Запуск без API-ключа (mock-режим)

Для проверки интерфейса без сети/ключа:

```bash
python main.py --mock          # или установите MOCK_MODE=true в .env
```

В mock-режиме агент возвращает имитированные ответы.

ниже.

## Сохранение контекста между запусками

Приложение автоматически сохраняет историю диалога и параметры агента
(модель, температура, max tokens, системный промпт) в **SQLite**
(`data/chat_history.db` по умолчанию):

- **Когда сохраняется:** после каждого успешного ответа ассистента и при
  закрытии окна/приложения.
- **Когда восстанавливается:** при запуске агент загружает контекст, и чат
  продолжается с того же места; в статус-баре появляется
  «Контекст восстановлен: N сообщений · модель …». Восстановленные параметры
  переопределяют значения из `.env`.
- **Очистка:** кнопка «Очистить историю» и применение нового системного
  промпта очищают историю и на диске.
- **Mock-режим** полностью изолирован: сообщения mock не сохраняются и не
  загружаются.
- Отключить персист можно в `.env`: `STORAGE_ENABLED=false`.

Проверка вручную:

1. Запустите `python main.py`, отправьте несколько сообщений (например,
   «Запомни, что мой любимый цвет — синий»).
2. Закройте приложение — убедитесь, что появился файл `data/chat_history.db`.
3. Запустите приложение снова: в чате видны прошлые сообщения, в статус-баре —
   «Контекст восстановлен…». Спросите агента «Какой мой любимый цвет?» — он
   помнит контекст.

## Подсчёт токенов

Агент считает токены и показывает их в статус-баре и в блоке **«Токены»** на
панели параметров:

| Показатель    | Что означает                                        | Точность |
|---------------|-----------------------------------------------------|----------|
| **Запрос**    | токены последнего запроса к API                     | точное значение из `usage` |
| **Ответ**     | токены, сгенерированные моделью                     | точное значение из `usage` |
| **Контекст**  | вся история в окне (system + сообщения, ≤50) — то, что уйдёт в следующий запрос | локальная оценка («≈») |
| **Сессия**    | суммарные токены за все обмены + оценка стоимости, USD | сумма точных значений API (+ оценка, если API не вернул `usage`) |

Как это работает:

- **Точные значения** берутся из `response.usage` (`prompt_tokens`,
  `completion_tokens`, `total_tokens`, а также поля кэша промпта, если API их
  вернул).
- **Оценка** выполняется модулем `src/tokens.py`: используется `tiktoken`
  (`cl100k_base`, так как у моделей DeepSeek своей кодировки нет), а если пакет
  не установлен или BPE-файл недоступен офлайн — встроенная эвристика. Оценка
  учитывает служебные токены формата чата и всегда помечается «≈».
- **Стоимость** считается только если заданы цены в `.env`; иначе отображается
  «—». Формула: `prompt/1M · цена_входа + completion/1M · цена_выхода`.
- **Статистика сессии сохраняется** в SQLite вместе с историей и
  восстанавливается при перезапуске; кнопка «Очистить историю» обнуляет её и в
  памяти, и на диске.
- **Mock-режим** помечает токены как оценочные и в хранилище не пишет.

Программный доступ:

```python
stats = agent.get_token_stats()      # request/response/context/session + имя счётчика
agent.count_tokens("текст")          # оценка произвольного текста
agent.count_history_tokens()         # оценка текущего контекста
agent.session_stats                  # копия накопленных сумм за сессию
result = agent.send_message("...")   # result["tokens"] — статистика обмена
```

## Стратегии управления контекстом и ветки

Агент умеет по-разному решать, **что именно уходит в запрос к модели**. Способ
выбирается переключателем **«Стратегия»** на панели параметров (или переменной
`STRATEGY` в `.env`) и сохраняется вместе с веткой диалога.

| Стратегия | Что уходит в API | Лишние запросы | Что помнит долго |
|---|---|---|---|
| `sliding_window` | `system` + последние `WINDOW_KEEP_LAST_N` сообщений | нет | ничего (только последние N) |
| `sticky_facts` | `system` + блок фактов + последние N сообщений | +1 запрос на ход | важное: цель, ограничения, предпочтения, решения, договорённости |
| `branching` | как в подстратегии активной ветки | зависит от подстратегии | всё в пределах выбранной ветки |

Важно: **окно не удаляет историю**. В API уходят только последние N сообщений,
но сама история остаётся в памяти, в SQLite и в чате — её видно целиком, и при
смене стратегии полный контекст возвращается.

### 1. Sliding Window (скользящее окно)

- в запрос идут `system` + ровно `WINDOW_KEEP_LAST_N` (по умолчанию 20) последних
  сообщений диалога;
- всё, что старше, в запрос не попадает (но остаётся в БД и в чате);
- самая дешёвая и предсказуемая стратегия: размер запроса ограничен сверху;
- расплата — «амнезия»: факт, сказанный в начале длинного диалога, модель уже
  не увидит.

### 2. Sticky Facts (липкие факты, key → value)

- ведётся отдельный блок фактов по категориям `goal`, `constraints`,
  `preferences`, `decisions`, `agreements`, например:
  `[preferences] любимый_цвет: синий`, `[goal] цель: написать отчёт`;
- после **каждого** хода вызывается служебный запрос к модели (инструкция
  помечена маркером `[[ОБНОВЛЕНИЕ_ФАКТОВ]]`), модель возвращает **строгий JSON**
  с полным обновлённым набором фактов; новое значение перезаписывает старое,
  `null` удаляет ключ, неизвестные категории и не-строковые значения
  отбрасываются;
- явные команды пользователя («запомни, что …», «запомни: ключ — значение»,
  «меня зовут …», «мой … — …») разбираются **локально** и срабатывают даже
  при сбое служебного запроса;
- если служебный запрос упал или вернул мусор — факты остаются прежними,
  ход не ломается, ошибка видна в окне «Контекст», попытка повторяется на
  следующем ходу;
- лимиты `FACTS_MAX_ITEMS` и `FACTS_MAX_TOKENS` вытесняют самые старые факты;
- токены и стоимость служебных запросов учитываются **отдельными счётчиками**
  (`facts_requests`, `facts_*_tokens`, `facts_cost_usd`) — статистика диалога
  ими не засоряется.

### 3. Branching (ветки диалога)

- **checkpoint**: кнопка «Создать от конца» в окне «Ветки» сохраняет текущее
  состояние диалога как новую ветку;
- **развилка от сообщения**: правый клик по любому сообщению в чате →
  «Создать ветку отсюда…» — новая ветка получает копию диалога **до** этого
  сообщения (индексы считаются без системного промпта), поэтому выбранную
  реплику можно задать иначе;
- **независимое продолжение**: ветки не смешиваются — сообщений одной ветки
  нет в другой;
- **переключение**: окно «Ветки» (кнопка «Ветки…») показывает таблицу веток
  (имя, стратегия, сообщений, фактов, создана, родитель), активная выделена;
  доступны «Переключиться», «Переименовать», «Удалить»;
- у каждой ветки **своя подстратегия** (`sliding_window` или `sticky_facts`) и
  **свои факты**: переключение ветки восстанавливает и то, и другое;
- ветки живут в SQLite (таблица `branches` + `messages.branch_id`/`seq`),
  активная ветка восстанавливается после перезапуска;
- старая БД (схема v1) мигрирует **без потери истории**: вся переписка
  становится веткой `main`;
- удалить последнюю ветку нельзя; ветку с дочерними — только каскадно
  (с подтверждением); число веток ограничено `BRANCH_MAX`.

### Переменные окружения

| Переменная | По умолчанию | Значение |
|---|---|---|
| `STRATEGY` | `sliding_window` | стратегия по умолчанию (`sliding_window` \| `sticky_facts` \| `branching`) |
| `WINDOW_KEEP_LAST_N` | `20` | сколько последних сообщений уходит в API |
| `FACTS_ENABLED` | `true` | обновлять факты служебным запросом после каждого хода |
| `FACTS_MODEL` | пусто | модель для извлечения фактов (пусто — модель диалога) |
| `FACTS_TEMPERATURE` | `0.0` | температура служебного запроса фактов |
| `FACTS_MAX_TOKENS` | `300` | лимит блока фактов в токенах |
| `FACTS_MAX_ITEMS` | `50` | максимум пар «ключ → значение» |
| `FACTS_PROMPT` | пусто | свой промпт-инструкция извлечения фактов |
| `BRANCH_MAX` | `20` | максимум веток |

Программный доступ:

```python
agent.available_strategies()      # ['sliding_window', 'sticky_facts', 'branching']
agent.get_strategy()              # текущая стратегия, окно, ветка, лимиты фактов
agent.set_strategy("sticky_facts")  # переключить стратегию (и запомнить для ветки)
agent.get_facts()                 # факты: категории, ключи, значения, токены
agent.remember("цель", "отчёт", "goal")
agent.forget("цель"); agent.clear_facts(); agent.update_facts_now(force=True)
agent.list_branches(); agent.get_active_branch()
agent.create_branch(from_index=2, name="ветка-A")   # 2 — индекс сообщения диалога
                                                    # (без system): копируется всё до него
agent.checkpoint(name="перед экспериментом")
agent.switch_branch(1)            # 1 — корневая ветка main
agent.rename_branch(1, "основная"); agent.delete_branch(2, cascade=False)
```

### Ограничения и что стоит помнить

- Окно **не** удаляет историю: в БД и в чате она остаётся целиком, ограничение
  действует только на содержимое запроса (поэтому память процесса растёт вместе
  с длиной диалога).
- Факты обновляются **раз за ход**: это +1 запрос к API на каждый ход
  (его токены и стоимость считаются отдельными счётчиками).
- Что не попало в факты — для модели потеряно: детали, не ставшие фактом и
  вышедшие за окно, недоступны.
- Ветки хранят **физические копии** префикса диалога (проще и надёжнее, чем
  общий предок), поэтому много больших веток = больше данных в БД.
- Смена стратегии не очищает историю; «Очистить историю» очищает **только
  активную ветку** вместе с её фактами — удаление ветки это отдельная операция.

## Модель памяти агента (memory layers)

Кроме стратегий контекста у агента есть **явная модель памяти из трёх слоёв**.
Слои хранятся **раздельно**, живут по своим правилам и пополняются **только
явно** — модель ничего не запоминает «тихо».

> Правило-мнемоника: **«диалог забывается окном, задача — её закрытием,
> долговременная память — только явным “Забыть”»**.

### Три слоя

| Слой | Что хранит | Где хранится | Область | Кто пишет | Когда исчезает | Что уходит в запрос |
|---|---|---|---|---|---|---|
| **short_term** (краткосрочная) | сообщения диалога + пометки «закреплено» | таблица `messages` БД чата (колонки `pinned`, `pin_note`) | активная ветка | автоматически каждый ход + вручную (кнопка «В диалог») | «Очистить историю», удаление ветки, открепление | последние `WINDOW_KEEP_LAST_N` сообщений + все закреплённые (в хронологическом порядке) |
| **working** (рабочая) | `task`: goal/status/plan/constraints/open_questions; `items`: `key→value` (`decision`/`artifact`/`note`) | `meta['working_memory']` + копия `meta['working_memory_<branch_id>']` в БД чата | ветка | вручную (кнопка/окно/команда) + подтверждённое предложение | «Новая задача», «Очистить рабочую», удаление/очистка ветки | отдельный `system`-блок (только task-поля и не-facts элементы) |
| **long_term** (долговременная) | `profile`, `decisions`, `knowledge` (`key→value` + `source`, `created_at`, `updated_at`) | **отдельный файл** `data/long_memory.db`, таблица `long_memory` | глобально (все ветки и сессии) | только вручную или подтверждённое предложение | только явное «Забыть» / «Очистить раздел» | отдельный `system`-блок (с приоритетным усечением по бюджету) |
| **pending** (предложения) | предложения классификации от LLM | таблица `pending_memory` в БД долговременной памяти | глобально | служебный LLM-запрос после хода | принятие/отклонение, «Очистить предложения» | **не уходит** до подтверждения |

### Состав запроса (порядок блоков)

Блоки памяти — это `system`-сообщения, поэтому `_limit_context()` их не вытесняет
(ограничение `MAX_HISTORY_MESSAGES` касается только сообщений диалога):

```
1. system-промпт агента
2. system: «ДОЛГОВРЕМЕННАЯ ПАМЯТЬ (профиль, решения, знания): …»   (если не пусто)
3. system: «РАБОЧАЯ ПАМЯТЬ (текущая задача): …»                    (если не пусто)
4. system: «ЗАКРЕПЛЁННЫЕ СООБЩЕНИЯ ДИАЛОГА: [индекс] роль: текст»  (если есть пины)
5. дальше — то, что вернула стратегия (system-промпт + факты + последние N)
```

Пустые слои не добавляются. Общий бюджет блоков — `MEMORY_MAX_TOKENS`
(по умолчанию 600); долговременная и рабочая память усекаются каждая по своему
бюджету (`MEMORY_LONG_MAX_TOKENS`, `MEMORY_WORKING_MAX_TOKENS`), приоритетное
усечение рабочего блока вытесняет сначала `plan`, затем `open_questions`,
`artifacts`, `constraints` — **`goal`/`status` не вытесняются никогда**.

### Явный выбор: кто и как пишет в слои

- Единственная точка записи — **`MemoryManager.route(...)`**; через неё проходят
  кнопки у сообщений, окно «Память…», текстовые команды и подтверждение
  предложений. Никакой код не пишет в слои в обход роутера.
- Неизвестный слой — **ошибка**, а не «положим куда-нибудь».
- Ключи→значения рабочей памяти для стратегии `sticky_facts` уходят **уже
  существующим блоком фактов** (тот же `FactsStore`), и рабочая память **не
  дублирует** их в своём блоке.
- **LLM только предлагает.** После хода (если `MEMORY_PROPOSE_LLM`) выполняется
  **один** служебный запрос с маркером `[[КЛАССИФИКАЦИЯ_ПАМЯТИ]]`, который
  возвращает строгий JSON с кандидатами и `confidence`. Кандидаты кладутся в
  **pending** и в слои **не попадают**; пользователь принимает (выбирая слой) или
  отклоняет их в окне «Память…». `MEMORY_AUTO_APPLY` существует, по умолчанию
  **false**, и его включение **нарушает принцип явного выбора слоя**.

### Кнопки у сообщений и окно «Память…»

Рядом с **каждым** сообщением в чате есть три кнопки:

- **💬 В диалог** — закрепить/открепить сообщение (краткосрочная память);
  закреплённое уходит в запрос, даже выйдя за `WINDOW_KEEP_LAST_N`. Лимит
  `MEMORY_PIN_MAX` (5): при превышении вытесняется самое старое закрепление.
  Когда сообщение закреплено, подпись меняется на «📌 Открепить»;
- **📋 В рабочую** — открывает окно «Сохранить в память» (рабочая предвыбрана)
  с цитатой-источником, редактируемым значением, полем «Ключ» и выпадающим
  «Вид» (`decision`/`artifact`/`note`);
- **🗄 В долговременную** — то же окно, но с выпадающим «Раздел»
  (`profile`/`decisions`/`knowledge`).

Уже сохранённое в слой помечается `✓`. Состояние кнопок берётся **из агента**
(пины и элементы с `source_message`, указывающим на это сообщение), поэтому
после перерисовки чата и перезапуска приложения кнопки показывают реальную
картину. Те же действия продублированы в **контекстном меню правого клика**
(«Сохранить в краткосрочную…», «Сохранить в рабочую память…», «Сохранить в
долговременную память…», «Показать, что сохранено об этом сообщении»).

Кнопка **«Память…»** на панели параметров открывает окно с вкладками:

- **«Краткосрочная (диалог)»** — таблица сообщений (`#`, роль, начало текста,
  закреплено), кнопки «Закрепить/Открепить» и «Открепить все»;
- **«Рабочая (задача)»** — редактируемые поля `goal`/`status`/`plan`/
  `constraints`/`open_questions`, таблица элементов и кнопки «Сохранить поля»,
  «Добавить элемент», «Удалить элемент», «Новая задача» (с переносом решений в
  долговременную память), «Очистить рабочую»;
- **«Долговременная»** — таблица (`раздел`, `ключ`, `значение`, `источник`,
  `создано`, `обновлено`), поиск, «Добавить», «Забыть», «Очистить раздел»,
  «Очистить долговременную», «Экспорт…», «Импорт…»;
- **«Предложения (pending)»** — кандидаты LLM с предложенным слоем и
  `confidence`, кнопки «Принять в …» (выбор слоя), «Отклонить», «Отклонить все»;
- **низ окна** — сводка по слоям и кнопка **«Что уходит в запрос»**, которая
  открывает read-only окно с результатом `agent.preview_context()` — построчно
  с пометкой слоя и токенов.

Все обращения к API по кнопкам выполняются в фоновом потоке (`_run_action`), UI
не «зависает».

### Переменные окружения

| Переменная | По умолчанию | Значение |
|---|---|---|
| `MEMORY_ENABLED` | `true` | общий выключатель модели памяти (`false` — поведение как раньше) |
| `MEMORY_WORKING_ENABLED` | `true` | рабочая память (задача, привязана к ветке) |
| `MEMORY_LONG_ENABLED` | `true` | долговременная память (профиль/решения/знания) |

| `MEMORY_LONG_MAX_ITEMS` | `200` | максимум записей долговременной памяти |
| `MEMORY_MAX_TOKENS` | `600` | общий бюджет блоков памяти в запросе |
| `MEMORY_LONG_MAX_TOKENS` | `300` | бюджет долговременной памяти |

```python
# Краткосрочная память (пины)
agent.pin_message(0); agent.unpin_message(0); agent.list_pinned()

# Рабочая память (своя у каждой ветки)
agent.get_working_memory(); agent.set_task_field("goal", "отчёт")
agent.add_working_item("дедлайн", "20 мая", "note")
agent.forget_working_item("дедлайн")
agent.clear_working_memory(); agent.start_new_task(carry_to_long=["архитектура"])

# Долговременная память (общая для всех веток и сессий)
agent.get_long_memory("profile"); agent.remember_forever("profile", "имя", "Алекс")
agent.forget_forever("profile", "имя"); agent.clear_long_memory("profile")
agent.export_long_memory(); agent.import_long_memory("data/memory_export.md")

# Предложения LLM (pending)
agent.get_pending_memory(); agent.accept_pending(3, layer="working")
agent.reject_pending(3); agent.clear_pending_memory()

# Отчёты и предпросмотр
agent.get_memory_report()   # элементы/токены/источник по каждому слою + budget + pending
agent.preview_context()     # реальный список сообщений запроса с пометкой слоя
agent.get_memory_settings() # настройки модели памяти
```

Готовый отчёт «какие данные попали в каждый слой» (заполняет все три слоя, печатает
`get_memory_report()` и построчный `preview_context()`) — в
`scripts/memory_report_demo.py`:

```bash
python scripts/memory_report_demo.py
```

### Ограничения и что стоит помнить

- **Долговременная память — отдельный файл** `data/long_memory.db`: она
  переживает «Очистить историю», удаление ветки и удаление `data/chat_history.db`.
  Очистить её можно только явно («Забыть» / «Очистить раздел» / «Очистить
  долговременную»).
- `clear_history()` («Очистить историю») очищает **только краткосрочную память
  активной ветки** (сообщения, пины) и её рабочую память; долговременная память
  сохраняется.
- **pending** — это только предложения: пока пользователь не подтвердил, в слои
  ничего не пишется.
- **Стоимость служебного запроса классификации считается отдельно** —
  счётчиками `memory_requests`, `memory_prompt_tokens`, `memory_completion_tokens`,
  `memory_estimated_tokens`, `memory_cost_usd` (статистика диалога ими не
  засоряется); ошибка классификации не ломает ход (WARNING + повтор на
  следующем ходу).
- В **mock-режиме** память живёт только «в процессе»: ни `chat_history.db`, ни
  `long_memory.db` не создаются.
- `MEMORY_ENABLED=false` (или отсутствие настроек памяти) возвращает поведение
  **ровно как раньше**: контекст запроса побайтово совпадает с прежним.

## Задачи как конечный автомат (FSM)

Кроме обычного чата агент умеет выполнять **задачи** — многошаговую работу
по схеме «план → выполнение шагов → проверка результата». Состояние задачи
описывает конечный автомат (:class:`~src.task_fsm.TaskFSM`), а вся история
живёт в отдельной БД SQLite (`data/tasks.db`), поэтому пауза, закрытие и
перезапуск приложения не теряют прогресс.

### Как создать задачу

Задача задаётся **сообщением в чате** — отдельной кнопки нет:

```
/задача Написать парсер логов
```

(работает и латинская команда `/task`; регистр не важен). Сообщение
остаётся в истории чата, а агент разбивает задачу на шаги и начинает
выполнение. Задача создаётся в **ручном режиме** — пользователь подтверждает
план и итог; режим можно переключить на лету в панели задачи.

### Состояния и режимы

| Состояние (`TaskStage`) | Значение |
|---|---|
| `idle` | задача не создана |
| `planning` | LLM формирует план |
| `awaiting_plan_approval` | ждём подтверждения плана (ручной режим) |
| `execution` | выполняем шаги (автоматически, без подтверждений) |
| `validation` | проверка результата |
| `awaiting_final_approval` | ждём финального подтверждения (ручной режим) |
| `paused` | пауза пользователем |
| `done` / `failed` / `cancelled` | завершена успешно / ошибка / отменена |

Режимы (`TaskMode`): **manual** — пользователь подтверждает переходы между
этапами (план и итоговый результат), **auto** — задача проходит все этапы
до `done` без остановок. **Шаги внутри выполнения не подтверждаются
никогда** — они идут цепочкой автоматически в обоих режимах: пользователь
управляет только переходами между этапами. Режим переключается на лету
выпадающим списком на панели задачи.

Ключевые правила автомата:

- **одна активная задача на профиль**: вторая не создаётся, пока активна
  первая (ошибка с подсказкой завершить/отменить существующую);
- **пауза с любого этапа** (`pause()`): текущая стадия сохраняется в БД
  (`stage_before_pause`), `resume()` возвращает задачу ровно в неё;
- **отклонение итога** (`reject_final`) возвращает задачу в выполнение для
  переделки; при провале валидации растёт `retry_count`, и при
  `retry_count > 3` задача автоматически переводится в `failed`;
- **каждый переход** пишется в журнал `task_events` (в БД) и в файл
  `fsm.log` (в корне проекта).

### Панель задачи в интерфейсе

После создания задачи над областью чата появляется панель:

```
┌────────────────────────────────────────────────────────────────────┐
│ ЗАДАЧА: Написать парсер логов           Режим: [Ручной ▾]  [Шаги ▸]│
│ Этап: Ожидание плана    Ожидается: подтверждение плана             │
│ ▓▓▓░░░░░░░░░░░░░░░░░░░░   Шаг 1 из 3: …                            │
│ [⏸ Пауза] [▶ Продолжить] [⏹ Стоп] [✓ Принять] [✗ Отклонить] [✕ Удалить] │
└────────────────────────────────────────────────────────────────────┘
```

- кнопки **активны строго по состоянию FSM**: «Пауза» — в рабочих стадиях
  (`planning`/`execution`/`validation`), «Продолжить» — на паузе (и для
  задачи, прерванной перезапуском), «Принять»/«Отклонить» — только на
  переходах между этапами (план, итог), «Стоп» — всегда, кроме
  `done`/`cancelled`, «✕ Удалить» — только для завершённых задач
  (`done`/`failed`/`cancelled`); активную задачу сначала нужно остановить;
- «Отклонить» запрашивает причину (необязательно) и возвращает план/итог
  на переделку;
- кнопка **«Шаги»** раскрывает список шагов плана со статусами
  (✓ выполнен / ⏳ выполняется / ✗ отклонён / · ожидает) и подсветкой текущего
  — это просмотр, а не управление;
- прогресс-бар и статус-бар обновляются при каждом переходе; в статус-баре
  дублируется краткая информация: `Задача: execution (2/3)`;
- итог завершённой задачи дописывается в чат как сообщение ассистента.

### Очистка задач

- **«✕ Удалить»** на панели задачи убирает завершённую задачу (`done` /
  `failed` / `cancelled`) из БД каскадно — вместе с шагами и журналом
  событий — и скрывает панель. Для активной задачи кнопка неактивна:
  сначала «⏹ Стоп»;
- **«Очистить задачи»** (верхняя панель) удаляет **все** задачи со всеми
  шагами и журналами, включая активную; перед удалением — подтверждение
  с числом задач и предупреждением про активную. После очистки можно
  сразу создать новую задачу сообщением `/задача …`.

### Восстановление после перезапуска

При запуске приложение ищет активную задачу профиля
(`stage NOT IN ('done','cancelled','failed')`):

- задача **не запускается автоматически** — если она была прервана в рабочей
  стадии, показывается «Задача прервана. Нажмите „Продолжить“…» и приложение
  ждёт явного решения пользователя;
- задача на паузе восстанавливается в `paused` (ждёт «Продолжить»);
- задача в стадии ожидания подтверждения ждёт «Принять»/«Отклонить».

При возобновлении агент **не переспрашивает контекст**: каждый служебный
LLM-вызов задачи получает system-блок `[Состояние задачи]` с названием,
этапом, текущим шагом, ожидаемым действием и историей выполнения всех шагов
— всё это собирается из БД, а не из истории чата.

### Переменные окружения

| Переменная | По умолчанию | Значение |
|---|---|---|
| `TASKS_ENABLED` | `true` | `false` — подсистема задач недоступна |
| `TASKS_PATH` | `data/tasks.db` | путь к БД задач (относительно корня проекта) |

### Программный доступ

```python
# Жизненный цикл (в UI задача создаётся сообщением /задача)
agent.start_task("Написать парсер логов", TaskMode.MANUAL)  # план
result = agent.continue_task()      # один этап (план/шаг/валидация)
result = agent.run_task()           # до остановки (ожидание/пауза/конец)
agent.pause_task(); agent.resume_task(); agent.cancel_task()

# Переходы между этапами (ручной режим)
agent.approve_plan(); agent.reject_plan("причина")
agent.approve_final(); agent.reject_final("причина")

# Режим, журнал, чат и очистка
agent.set_task_mode(TaskMode.AUTO)    # переключение на лету
agent.active_task                     # текущая задача (или None)
agent.get_task_events()               # журнал переходов
agent.restore_task()                  # восстановление после запуска
agent.note_task_message("текст")      # сообщение о задаче в истории чата
agent.delete_task()                   # удалить текущую (завершённую) задачу
agent.delete_task(3)                  # удалить задачу по id (каскадно)
agent.clear_tasks()                   # удалить ВСЕ задачи (каскадно)
```

Тесты (пауза на planning/execution, перезапуск, отклонения плана и итога,
авто-режим, цепочка шагов без подтверждений, смена режима на лету, контекст
без повторных вопросов, «одна активная задача», каскадное удаление, команда
`/задача`) — в `tests/test_task_fsm.py`.

### Явные переходы: матрица, контроллер, маркеры

Переходы задачи определяет декларативная матрица
`ALLOWED_TRANSITIONS` (в `src/task_fsm.py`), а применяет их **только**
контроллер `TaskFSM.transition_to()` — три уровня защиты:

1. **Промпт**: пока есть активная задача, system-промпт получает блок
   «[МАРКЕРЫ СОСТОЯНИЯ ЗАДАЧИ]» — LLM ставит в конце ответа один маркер
   (`[PLAN_READY]`, `[STEP_DONE]`, `[ALL_STEPS_DONE]`, `[VALIDATION_OK]`,
   `[VALIDATION_FAIL]`, `[NEED_INPUT]`) и видит текущую стадию с
   допустимыми переходами;
2. **Контроллер**: намерение из ответа извлекает
   `TaskResponseParser` (маркер → эвристика «план готов» → fail-safe
   `None`), но переход выполняется только если он разрешён матрицей;
   запрещённые отклоняются с `InvalidTransitionError`
   (из `done`/`cancelled` — `TerminalStateError`);
3. **БД**: стадию в SQLite обновляет только FSM.

Ключевой принцип: **LLM предлагает действие, но решение о переходе
принимает код**. Все попытки переходов — и успешные, и отклонённые —
пишутся в журнал `task_events` (`rejected_transition` с причиной;
много отклонённых — сигнал переработать промпт, они также дублируются
в `fsm_warnings.log`). Ответ без маркера ничего не ломает: в журнал
пишется `unresolved_transition`, а в статус-баре появляется подсказка.

Ключевые запреты, которые защищает матрица: нельзя в `execution` без
утверждённого плана (в manual `PLANNING → EXECUTION` запрещён — только
через подтверждение), нельзя в `done` мимо валидации, нельзя вернуться
из `done`/`cancelled`, откат из `validation` разрешён не более
`TASKS_MAX_RETRIES` раз (по умолчанию 3; сверх лимита задача `FAILED`,
а перезапуск `FAILED → PLANNING` обнуляет счётчик). Пауза доступна с
любой активной стадии, «Продолжить» возвращает в стадию до паузы — она
хранится в БД и восстанавливается из журнала даже после перезапуска.

В панели задачи под этапом — граф состояний на Canvas: текущая стадия —
зелёный узел, пройденные — серые, будущие — белые, терминальные исходы
(`done` — синий, `failed` — красный, `cancelled` — серый) и жёлтая пауза
показаны сбоку; под графом перечислены допустимые переходы текущей
стадии.

## Инварианты: жёсткие правила проекта

Инвариант — правило, которое **всегда истинно** для проекта: стек, архитектура,
безопасность, бизнес-правила. Это отдельный слой поверх профиля: профиль
описывает, **как отвечать** (мягкие правила, уступают запросу), инвариант —
**что можно делать** (жёсткие правила, не переопределяются даже прямым
запросом в чате — изменить инвариант можно только через вкладку «Инварианты»).

```python
# Двухуровневая система областей действия:
#   global  (profile_id = NULL)      — фундаментальные правила для всех профилей
#   profile (profile_id = <id>)      — правила конкретного профиля
# В system-промпт попадают: global + инварианты активного профиля,
# сгруппированные по категориям и отсортированные по приоритету (важные выше).
```

Порядок слоёв в system-промпте: базовая инструкция → **инварианты** → профиль →
контекст → долгосрочная память → правила приоритета.

Что делает агент:

- при каждом запросе учитывает инварианты (блок в system-промпте);
- отказывается выполнять запросы, нарушающие инвариант, и объясняет отказ:
  какой инвариант нарушен, почему, какие альтернативы возможны;
- не переубеждается настойчивыми запросами («ну всё-таки покажи PyQt»);
- не упоминает инварианты, если они не нарушаются.

Пост-проверка (второй LLM-вызов после каждого ответа):

1. валидатор проверяет ответ на нарушение инвариантов (в том числе косвенное —
   «пример в коде» тоже нарушение);
2. при нарушении агент перегенерирует ответ с явным напоминанием
   «Предыдущий ответ нарушил инвариант: …»;
3. перегенераций не больше `MAX_REGENERATIONS` (по умолчанию 2); если
   нарушение осталось — последний ответ + предупреждение в UI;
4. ответы короче `MIN_RESPONSE_LENGTH` (100 символов) не проверяются;
5. отказы и перегенерации пишутся в лог `invariant_violations` (SQLite).

При сохранении инварианта в UI запускается LLM-проверка конфликтов: если новое
правило противоречит существующим, показывается предупреждение с кнопками
«Всё равно сохранить» / «Отменить» — сохранение НЕ блокируется.

UI:

- вкладка **«Инварианты»**: слева категории (7 предустановленных, три системные
  — Безопасность/Архитектура/Стек — удалить нельзя), справа инварианты выбранной
  категории с маркерами `[G]` (глобальный) / `[P]` (профильный);
- кнопка **«📋 Инварианты»** в панели задачи открывает модальное окно с
  активными правилами (активный профиль + Global) и кнопкой «Перейти к
  редактированию»;
- статус-бар: `Инвариантов: N (глобальных: X, профильных: Y)`.

Хранилище: те же `data/chat_history.db`, таблицы `invariant_categories`,
`invariants`, `invariant_violations` (создаются миграцией; при первом запуске
добавляются предустановленные категории и 1–2 инварианта-примера — их можно
удалить).

Конфигурация (.env):

```bash
ENABLE_POST_CHECK=true     # пост-проверка ответов (второй LLM-вызов)
MAX_REGENERATIONS=2        # лимит перегенераций при нарушении
MIN_RESPONSE_LENGTH=100    # ответы короче не проверяются
```

## Управление контекстом (сжатие истории в конспект) — legacy

> Этот режим оставлен для обратной совместимости и **не входит** в переключатель
> стратегий: если агенту переданы настройки `summary_settings` и не выбрана
> стратегия, работает описанная ниже суммаризация. Приложение (`main.py`)
> стратегии передаёт всегда, поэтому в интерфейсе суммаризации нет.

Чтобы длинный диалог не упирался в лимит модели и не терял контекст,
приложение сжимает его старую часть в **конспект (summary)**:

- последние **N** сообщений (`SUMMARY_KEEP_LAST_N`, по умолчанию 10) всегда
  уходят в модель «как есть»;
- когда «лишних» (не покрытых конспектом) сообщений накапливается **K**
  (`SUMMARY_EVERY_N`, по умолчанию 10), запускается служебный запрос к модели:
  она объединяет старый конспект и новый блок в один;
- в API уходит схема
  `[system-промпт] → [system: «Краткое содержание предыдущего диалога: …»] → [непокрытые сообщения]`,
  поэтому фактический размер контекста ограничен `N + K − 1` сообщениями плюс
  конспект;
- **полная история диалога не теряется** — она остаётся в памяти и в SQLite
  (её видно в чате, и по ней можно пересобрать конспект);
- конспект хранится отдельно (в `meta['summary']` со счётчиком `covered`) и
  восстанавливается при перезапуске — повторного сжатия на старте не происходит;
- **токены и стоимость служебных запросов учитываются отдельными счётчиками**
  (`summary_requests`, `summary_*_tokens`, `summary_cost_usd`), статистика
  диалога ими не засоряется;
- если служебный запрос не удался, **ничего не удаляется**: история уходит как
  есть, ошибка видна в статусе, попытка повторяется при следующем триггере;
  аварийный предел `MAX_HISTORY_MESSAGES` ограничивает только отправляемую часть;
- при выключенном сжатии (`SUMMARY_ENABLED=false`) поведение прежнее —
  история урезается по `MAX_HISTORY_MESSAGES`.

Кнопка **«Контекст…»** на панели параметров открывает окно с текстом конспекта,
сведениями (сколько сообщений покрыто, токены, время и модель обновления) и
кнопками **«Обновить»** (принудительное сжатие в фоновом потоке) и
**«Очистить»**. В блоке «Токены» видно `Конспект: ≈X токенов · покрыто Y сообщ.`,
а в статус-баре — `ctx: ≈X (Y сообщ. в конспекте)`.

Программный доступ:

```python
agent.get_summary()                  # текст конспекта, covered, токены, ошибка
agent.summarize_now(force=True)      # принудительное сжатие
agent.clear_summary()                # очистить конспект (история остаётся)
agent.count_context_tokens()         # токены того, что уйдёт в следующий запрос
```

### Как работает агент

1. **Конструктор** сохраняет системный промпт первым сообщением истории,
   проверяет параметры (`_validate_parameters`) и — если передано хранилище
   `ContextStore` — **загружает сохранённый контекст**: восстановленные
   параметры переопределяют значения из конструктора/.env, история заполняется
   из БД.
2. **`send_message(user_input)`** — добавляет сообщение пользователя, отправляет
   *всю* историю (`_build_request`), измеряет время запроса, разбирает ответ
   (`_handle_response`), добавляет ответ ассистента и возвращает словарь
   `{text, model, tokens, response_time, finish_reason, error}`. После каждого
   успешного обмена контекст сохраняется в БД (`src/storage.py`).
3. При ошибке API сообщение пользователя **откатывается** из истории — кнопка
   «Повторить» не дублирует его, и метод возвращает `error`, а не исключение.
4. В режиме стратегий «сырая» история **не урезается**: sliding window
   отбрасывает сообщения только в самом запросе, поэтому история целиком
   остаётся в памяти и в БД и возвращается при смене стратегии. Ограничение
   `MAX_HISTORY_MESSAGES` действует только в legacy-режиме (без стратегий) и
   как аварийный предел отправляемого контекста.
5. Все публичные операции выполняются под `threading.RLock`.
6. `clear_history()` и смена системного промпта очищают историю и **на диске**;
   `close()` делает финальный flush при закрытии окна/приложения.
7. **Токены** учитываются после каждого успешного обмена: точные значения из
   `usage` (или оценка счётчиком `src/tokens.py`), суммарная статистика сессии
   сохраняется вместе с историей; при ошибке API счётчики не меняются.
   Служебные запросы (сжатие, обновление фактов) считаются **отдельными**
   счётчиками `summary_*` и `facts_*`.
8. **Контекст** собирается перед каждым запросом стратегией
   (`src/strategies.py`): `sliding_window` отдаёт `system` + последние N
   сообщений, `sticky_facts` — ещё и блок фактов отдельным system-сообщением.
   Артефакты (факты, конспект) и сообщения принадлежат **активной ветке**
   (`src/branches.py`), поэтому переключение ветки меняет и контекст, и стратегию.
   Legacy-режим (summary) работает, только если стратегия не задана.

### Как работает интерфейс

- Запрос выполняется в **фоновом потоке**; результат передаётся в главный поток
  через `queue.Queue`, которую опрашивает `root.after` — безопасный паттерн для
  Tkinter, поэтому окно не «замерзает».
- Источник правды для чата — **история агента**: после каждого результата
  область чата перерисовывается из `agent.history`, что исключает расхождения.
  Если агент восстановил контекст при запуске, чат сразу показывает прошлый
  диалог, а статус-бар сообщает «Контекст восстановлен: N сообщений …».
- Параметры модели/температуры/токенов применяются к агенту мгновенно;
  системный промпт — только по кнопке **«Применить»** с предупреждением о сбросе
  истории.
- Блок **«Токены»** и правая часть статус-бара обновляются после каждого ответа и
  после действий, меняющих историю (очистка, смена промпта, запуск).
- Поле ввода: подсказка «Введите сообщение…» — **отдельная метка поверх поля**
  (а не текст внутри), поэтому ввод и вставка с ней не смешиваются, и после
  отправки можно сразу писать следующий запрос. Поддерживаются `Ctrl+V`
  (в **любой раскладке** — клавиша определяется по физическому коду, а не по
  keysym, который при русской раскладке равен `Cyrillic_em`), `Shift+Insert`,
  правая кнопка мыши и текст любого размера; высота поля автоматически растёт
  до 10 строк, дальше работает прокрутка. Очень длинные сообщения (свыше
  20 000 символов) в области чата отображаются частично — сама отправка
  не ограничена (лимит задаёт только контекст модели).
- Ошибки показываются в статус-баре и в диалоге с кнопкой **«Повторить»**.
- API-ключ в сообщениях об ошибках никогда не раскрывается.

## MCP-клиент: панель инструментов

Приложение подключается к MCP-серверам (Model Context Protocol) через
официальный Python SDK `mcp`. Реализованы оба протокольных запроса:
получение и просмотр списка инструментов (`tools/list`) и вызов
инструмента с результатом в UI (`tools/call`, кнопка **▶ Вызвать**).
В комплекте — собственный локальный сервер `my_git_server.py`
(FastMCP, stdio) с тремя инструментами над Git (см. ниже).

### Как это работает

```
┌──────────────────────────────────────────────┬──────────────┐
│                 ОБЛАСТЬ ЧАТА                 │  MCP    [◀]  │
│                                              │ ● Подключён  │
│                                              │ 26 инструментов │
│                                              │ [🔄 Обновить]│
│                                              │ ──────────── │
│                                              │ ▸ wikipedia_summary │
│                                              │ ▸ github_search     │
│                                              │ ▸ arxiv_search      │
│                                              │ …                   │
└──────────────────────────────────────────────┴──────────────┘
        │ «Обновить»
        ▼
MCPWorker (поток, daemon) → asyncio.run(MCPClient.list_tools())
    → ClientSession + stdio_client (SDK mcp)
        → подпроцесс: npx -y open-internet-mcp → tools/list
    ← [MCPTool(name, description, input_schema), …]
    ← callback → queue → root.after → панель (главный поток Tk)
```

- **По умолчанию** — сервер `open-internet-mcp` (коллекция из 26 открытых
  API без ключей и аккаунтов; транспорт stdio). Для запуска нужен
  установленный Node.js ([nodejs.org](https://nodejs.org)): `npx` скачает
  пакет при первом подключении (поэтому таймаут по умолчанию 30 секунд).
- **Потокобезопасность**: запрос выполняется в отдельном потоке
  (`MCPWorker`), результат доставляется в UI через `queue.Queue` +
  `root.after` — тот же паттерн, что у задач (FSM). UI не блокируется.
- **Каждый запрос** — отдельная сессия: процесс сервера запускается,
  проходит handshake (`initialize`), отдаёт список и завершается.
- **Журнал**: `mcp.log` в корне проекта — события клиента и stderr
  сервера (прогресс npm, ошибки запуска).

### Элементы панели «MCP» (справа от чата)

| Действие | Элемент |
|---|---|
| Статус подключения | индикатор ● : серый «Не подключён», жёлтый «Загрузка...», зелёный «Подключён \| N инструментов», красный «Ошибка: …» |
| Запросить список инструментов | кнопка **🔄 Обновить** (на время запроса блокируется) |
| Вызвать инструмент | кнопка **▶ Вызвать** на карточке → диалог: поля по inputSchema (обязательные помечены `*`), кнопка **Выполнить**, результат — pretty-JSON в том же окне, кнопка **Копировать результат** |
| Посмотреть описание и параметры | клик по карточке или кнопка **Параметры** → модальное окно с описанием и JSON inputSchema; кнопка **Копировать JSON** |
| Свернуть/развернуть панель | кнопка **◀ / ▶**; состояние сохраняется в SQLite (`data/app_state.db`, таблица `app_state`) |
| Пустой список | не считается ошибкой: «Подключён \| 0 инструментов» |

Вызов инструмента идёт в отдельном daemon-потоке (`MCPToolCallWorker`),
результат доставляется в диалог через `queue.Queue` + `after` — UI не
блокируется; окно можно закрыть во время выполнения. Пустые необязательные
поля не передаются (срабатывает серверное значение по умолчанию), типы
проверяются перед запуском (integer/number/boolean).

### Обработка ошибок

| Ситуация | Что видит пользователь |
|---|---|
| `npx` не найден (нет Node.js) | красный статус + messagebox: «Установите Node.js: https://nodejs.org» |
| Сервер не запустился | текст ошибки запуска; stderr сервера — в `mcp.log` |
| Таймаут (по умолчанию 30 с) | «Сервер не ответил за 30 секунд …» |
| Некорректный ответ сервера | «Сервер вернул некорректный ответ…» |
| SDK `mcp` не установлен | подсказка: `pip install "mcp>=1.28,<2"` |

### Конфигурация (`.env`)

```dotenv
MCP_ENABLED=true                                  # False — панель не создаётся
MCP_SERVER_COMMAND=npx -y open-internet-mcp       # команда запуска сервера
MCP_TIMEOUT=30                                    # таймаут handshake/tools/list, сек
MCP_LOG_PATH=mcp.log                              # журнал клиента и stderr сервера
APP_STATE_PATH=data/app_state.db                  # состояние UI (сворачивание панели)
```

`MCP_SERVER_COMMAND` разбирается через shlex — можно указать любой
stdio-сервер, например `uvx some-mcp-server` или путь к локальному
скрипту. Для тестов без Node.js и сети в репозитории есть фикстура
FastMCP-сервера: `python -u tests/fixtures/mcp_echo_server.py` —
её и использует офлайн-набор тестов (`tests/test_mcp.py`, 47 тестов).

Для локальных python-серверов действуют два правила-resolve: голый
`python`/`python3` заменяется на интерпретатор приложения
(`sys.executable` — у него точно есть SDK `mcp`), а относительный
`*.py`-путь в последнем аргументе разрешается от корня проекта.
То есть `MCP_SERVER_COMMAND=python -u my_git_server.py` работает из
любого рабочего каталога.

## Собственный MCP-сервер Git (my_git_server.py)

Локальный MCP-сервер в корне проекта (`my_git_server.py`, FastMCP,
транспорт stdio — без сети и хостинга): запускается приложением как
подпроцесс и отдаёт реальные данные локального Git. Подключается
одной строкой в `.env`:

```dotenv
MCP_SERVER_COMMAND=python -u my_git_server.py   # собственный сервер
MCP_GIT_REPO_PATH=                              # "" — корень проекта
```

### Инструменты

| Инструмент | Вход | Выход |
|---|---|---|
| `get_git_log` | `repo_path: str`, `limit: int = 10` (зажимается к 1…500) | последние N коммитов: `{hash, author, date, message}`; пустой репозиторий → `[]` |
| `get_git_status` | `repo_path: str` | `{modified, staged, untracked}` (по `git status --porcelain`; переименование — новым путём) |
| `get_git_branches` | `repo_path: str` | список локальных веток |

Типы параметров превращаются декоратором `@mcp.tool()` в inputSchema,
docstring — в описание для LLM/панели. Несуществующий путь → результат
с `{"error": "..."}` (не исключение транспорта).

### Поток вызова (кнопка «Вызвать»)

```
[▶ Вызвать] на карточке → диалог (поля по inputSchema, repo_path
  подставлен из MCP_GIT_REPO_PATH) → «Выполнить»
    → MCPToolCallWorker (daemon-поток) → asyncio.run(MCPClient.call_tool(...))
        → ClientSession + stdio_client → подпроцесс my_git_server.py → tools/call
    ← structuredContent (pretty-JSON) → queue → after → диалог (главный поток)
```

Каждый вызов — отдельная сессия (запуск сервера → initialize → call →
завершение процесса), как и для списка инструментов. Ошибки транспорта
оборачиваются в `MCPTimeoutError`/`MCPConnectionError` и показываются
в диалоге.

### Важные детали реализации

- **`stdin=subprocess.DEVNULL` в `_run_git` обязателен.** Дочерний
  процесс не должен наследовать stdin MCP-сервера (JSON-RPC-канал):
  на Windows + anyio stdio такой spawn зависает навсегда, и клиент
  упирается в таймаут (проверено минимальным воспроизведением).
- Результат вызова извлекается из `structuredContent` ответа MCP
  (pretty-JSON; у FastMCP значение обёрнуто в `{"result": ...}`),
  без него — склеенные текстовые блоки `content`.
- `MCP_ENABLED` приводится к bool на уровне `_coerce` — `false` в
  `.env` действительно выключает панель.

### Тесты

`tests/test_mcp_server.py` — 45 тестов, покрывают 9 сценариев приёмки:
запуск сервера-подпроцесса, регистрация 3 инструментов с inputSchema,
`list_tools`/`call_tool` против реального сервера (git-репозитории
создаются в `tests/tmp_git_server/`, в `.gitignore`), ошибка
несуществующего пути, UI-диалог (форма, префилл, валидация, результат,
ошибка) и отзывчивость UI во время вызова. Тесты требуют SDK `mcp` и
git в PATH, иначе пропускаются.

## MCP-сервер «Smart Reminder» (reminder_server.py)

Собственный MCP-сервер напоминаний в корне проекта
(`reminder_server.py`, FastMCP, **Streamable HTTP, stateful**).
В отличие от Git-сервера (stdio-подпроцесс клиента) он живёт
самостоятельно: привязан к `127.0.0.1` (хостинг в интернете запрещён),
хранит данные в SQLite (`reminders.db` в корне) и работает 24/7 —
переживает перезапуски приложения.

### Запуск и жизненный цикл

```dotenv
REMINDER_ENABLED=true          # false — без напоминаний
REMINDER_SERVER_HOST=127.0.0.1 # только локальные адреса пропускаются
REMINDER_SERVER_PORT=8000
REMINDER_TOOLCALL_MAX_ROUNDS=5 # лимит циклов tool calling за ход
```

При старте приложения (`main.py` → `ChatApplication.launch_reminder_server`):

1. `ReminderServerLauncher.is_server_running()` — TCP-проверка порта;
2. если порт свободен — сервер запускается **в новом окне консоли**
   (`CREATE_NEW_CONSOLE`): там видны логи uvicorn и планировщика;
3. если порт занят (сервер от прошлой сессии) — запуск НЕ повторяется;
4. закрытие приложения сервер НЕ останавливает (`stop()` — no-op,
   сервер 24/7), останавливается только слушатель SSE в приложении.

Кнопка **«🔔 Перезапустить сервер»** в верхней панели поднимает упавший
сервер (работающий намеренно не трогает — БД не должна пострадать);
рядом индикатор: «сервер запущен» / «сервер не запущен» / «проверяется…».

### Инструменты

| Инструмент | Вход | Выход |
|---|---|---|
| `add_reminder` | `text: str`, `interval_minutes: int`, `repeat: bool = False` | `{id, text, interval_minutes, repeat, next_due_at}`; `interval_minutes <= 0` → `{"error": ...}` |
| `get_due_reminders` | — | сработавшие: `[{id, text, triggered_at}]`; **транзакционно** сдвигает `next_due_at` повторяющимся и деактивирует одноразовые |
| `get_all_reminders` | — | активные, по времени срабатывания |
| `delete_reminder` | `reminder_id: int` | `{"success": true/false}` |
| `get_stats` | — | `{total, active, triggered_today, avg_interval}` |

### Планировщик и SSE-уведомления

Внутри сервера APScheduler (`BackgroundScheduler`) каждую минуту
выполняет `check_due_reminders`: из-за срока выбирает напоминания,
пишет срабатывания в `reminder_log` и рассылает уведомления
`notifications/message` (`send_log_message`) всем подписанным MCP-сессиям.

Подписка: каждый вызов инструмента регистрирует сессию клиента в
реестре сервера (`_register_session`). Инструменты — `async` и работают
в event loop uvicorn, где доступен `asyncio.get_running_loop()`
(у sync-инструментов FastMCP его нет — они идут через пул потоков
anyio, и привязку «сессия → loop» сделать невозможно). Рассылка —
`asyncio.run_coroutine_threadsafe` из потока APScheduler.

Клиент (`src/reminder_client.py`): после handshake слушатель
регистрирует свою сессию служебным вызовом `get_stats` и повторяет
регистрацию раз в 60 секунд (health-check + защита от перезапуска
сервера). Уведомления приходят в `message_handler` сессии и через
очередь попадают в чат — блок «🔔 Напоминание: …» в нижней части
(в историю диалога агента они НЕ попадают).

### Tool calling: «напомни выпить кофе через 5 минут»

```
DeepSeekAgent.send_message
  → _get_tools_for_llm()      # tools/list по HTTP, кэш 60 с; сервер
                              # недоступен → запрос БЕЗ tools (диалог живёт)
  → chat.completions.create(tools=…)   # формат OpenAI/DeepSeek
  ← message.tool_calls                 # LLM выбрала add_reminder
  → ReminderMCPClient.call_tool(...)   # tools/call по HTTP
  → messages += [assistant(tool_calls, reasoning_content), tool(result)]
  → chat.completions.create(...)       # финальный ответ с учётом результата
```

Детали: промежуточные сообщения существуют только внутри цикла —
в историю диалога и SQLite попадает финальный текст (персистентность
и стратегии контекста не затронуты); `reasoning_content` Thinking Mode
передаётся обратно вместе с `tool_calls` (по ТЗ), при отказе API —
автоматический повтор без него; usage нескольких вызовов суммируется;
лимит циклов — `REMINDER_TOOLCALL_MAX_ROUNDS`; ошибка MCP-вызова
уходит модели как результат с `"error"`, ход не прерывается.
Выполненные вызовы показываются в чате служебными строками «🛠 …».

### Ручной запуск (для проверки)

```
python reminder_server.py                    # порт 8000, reminders.db
python reminder_server.py --port 8010 --db D:\tmp\rem.db
python reminder_server.py --check-seconds 2  # ускоренный тик (для тестов)
```

### Тесты

`tests/test_reminder_server.py` — 43 теста на 12 сценариев приёмки ТЗ:
impl-логика на временных БД (переходы one-shot/repeat, статистика,
удаление, валидация), HTTP-интеграция с реальным сервером-подпроцессом
(5 инструментов с inputSchema, add/due/repeat/stats/delete по HTTP,
SSE-уведомление end-to-end), лаунчер (новое окно, защита от дублей,
no-op stop), tool calling агента (офлайн, фейковый API-клиент: tools в
запросе, роль `tool`, reasoning_content, суммирование usage, лимит
раундов, недоступный сервер), конфиг `REMINDER_*` и UI (индикатор,
кнопка, уведомление в чате). Интеграционные тесты требуют SDK `mcp`,
иначе пропускаются.

## MCP-сервер «News» и agentic loop (news_server.py)

Собственный MCP-сервер новостей (`news_server.py`, FastMCP,
Streamable HTTP, **порт 8001**, только 127.0.0.1). Как и reminder-сервер,
запускается приложением в новом окне консоли и живёт 24/7
(`NewsServerLauncher` — тот же базовый класс, что у напоминаний).

```dotenv
NEWS_ENABLED=true           # false — без новостей и автозапуска
NEWS_SERVER_PORT=8001
NEWS_SUMMARY_MODEL=         # "" — deepseek-v4-flash
NEWS_OUTPUT_DIR=            # "" — output/ в корне проекта
NEWS_RSS_FEEDS=             # "" — встроенные ленты (см. ниже)
```

### Инструменты (цепочку строит LLM)

| Инструмент | Вход | Выход |
|---|---|---|
| `search_news` | `topic: str`, `limit: int = 10` | JSON `{"topic", "count", "news": [{title, link, summary, source}]}`; ничего не найдено → `{"error": ...}` |
| `summarize_text` | `text: str` | Markdown-сводка (DeepSeek API внутри сервера); ошибка → сообщение + сырой текст |
| `save_to_file` | `content: str` | абсолютный путь `output/news_YYYYMMDD_HHMMSS.md` |

RSS-ленты по умолчанию: **Google News с поиском по теме**
(`https://news.google.com/rss/search?q={topic}&hl=ru&gl=RU&ceid=RU:ru`)
+ статические `cnews.ru`, `3dnews.ru`, `habr.com`, `kommersant.ru`,
`lenta.ru`. Загрузка каждой ленты — с таймаутом 10 с; недоступная
лента **пропускается** (ошибки собираются в ответ), поиск продолжается
по остальным.

**Шаблон `{topic}`** — поисковые ленты: если URL содержит `{topic}`,
тема подставляется в запрос (с URL-кодированием) и фильтруется на
стороне провайдера — локальный буквальный фильтр к такой ленте не
применяется (её записи уже релевантны). Это даёт полноценный поиск по
произвольной теме; статические ленты в дефолте — запас на случай,
когда поисковая недоступна. Любая поисковая RSS подключается строкой
в `.env`:

```dotenv
NEWS_RSS_FEEDS=google=https://news.google.com/rss/search?q={topic}&hl=ru&gl=RU&ceid=RU:ru
```

Локальный фильтр статических лент — вхождение темы в заголовок или
описание без учёта регистра.

`summarize_text` — это **отдельный вызов DeepSeek API** внутри
news-сервера (ключ `DEEPSEEK_API_KEY` наследуется от приложения либо
дочитывается из `.env`): результат возвращается инструментом MCP и в
историю чата не попадает. Лимит токенов — `NEWS_SUMMARY_MAX_TOKENS`
(дефолт 8000): thinking-модели тратят часть бюджета на reasoning,
поэтому малый лимит (например 1500) обрезает сводку
(`finish_reason=length`). При обрезке выполняется повтор с удвоенным
лимитом, при пустом ответе — то же самое, затем fallback: LLM-агент
получает сырые новости и сводит их сама.

### Как работает agentic loop

```
Пользователь: «Прочитай свежие новости про технологии и сохрани сводку»
  → LLM (tools обоих серверов)      → tool_calls: search_news
  → код вызывает MCP, результат     → возвращается в LLM
  → LLM                             → tool_calls: summarize_text
  → код вызывает MCP, сводка        → возвращается в LLM
  → LLM                             → tool_calls: save_to_file
  → код вызывает MCP, путь файла    → возвращается в LLM
  → LLM: «Готово! Сохранил сводку в файл: …»
```

Реализация — тот же цикл `DeepSeekAgent._call_api`, что и для
напоминаний, обобщённый на несколько MCP-серверов:

* tools reminder-сервера, news-, geo- и weather-серверов сливаются в
  один список (кэш по клиенту, TTL 60 с); маршрут «имя инструмента →
  сервер» обновляется при каждой сборке, вызовы уходят своему серверу;
* лимит циклов «LLM → tool_calls → результат → LLM» — 5
  (`REMINDER_TOOLCALL_MAX_ROUNDS`), зацикливание обрывается;
* **правила инструментов** добавляются в system-промпт, когда tools
  доступны: итоговая сводка сохраняется в файл через `save_to_file`,
  а в чат выводится краткий ответ с путём (без дублирования текста);
* **самовосстановление**: при ошибке подключения клиент однократно
  поднимает свой сервер (`restart_hook` → `ensure_running` — проверка
  порта, запуск, ожидание выхода на порт) и повторяет вызов в рамках
  того же хода; таймаут `tools/call` — 180 с (summarize_text с
  thinking-моделью работает дольше 30 с);
* результат `save_to_file` распознаётся агентом: путь попадает в
  `result["file_path"]` → UI рисует в чате блок «📂 Файл сохранён»
  с кнопкой **«📂 Открыть файл»** (`os.startfile`; кнопка встроена в
  область чата через `window_create` и переживает перерисовку, хвост —
  5 файлов);
* ошибка любого MCP-вызова уходит LLM как результат с `"error"` —
  ход диалога не прерывается.

### Тесты

`tests/test_news_server.py` — 32 теста на 9 сценариев приёмки ТЗ:

`tests/fixtures/rss_news.xml`, подстановка и URL-кодирование `{topic}`,

## Цепочка MCP-серверов «гео → погода» (geo_server.py + weather_server.py)

Два собственных MCP-сервера (FastMCP, Streamable HTTP, только 127.0.0.1),
каждый в своём окне консоли, 24/7 (`GeoServerLauncher` /
`WeatherServerLauncher` — тот же базовый класс, что у напоминаний и
новостей). **Порты 8002 и 8003**: порт 8001 уже занят news-сервером.

```dotenv
GEO_ENABLED=true            # false — без геолокации и автозапуска
GEO_SERVER_PORT=8002
WEATHER_ENABLED=true        # false — без погоды и автозапуска
WEATHER_SERVER_PORT=8003
```

### Инструменты

| Сервер | Инструмент | Вход | Выход |
|---|---|---|---|
| geo (8002) | `get_user_city` | — | название города (`"Berlin"`) или `"Unknown"`; источник — ip-api.com (без ключа, 45 запросов/мин) |
| weather (8003) | `get_weather` | `city: str` | JSON `{"city", "temperature", "wind_speed", "humidity"}`; город не найден/нет сети → `{"error": ...}`; источник — Open-Meteo (без ключа, два шага: геокодинг → прогноз) |

### Как LLM строит цепочку

```
Пользователь: «Какая сегодня погода?»
  → LLM                             → tool_calls: get_user_city        (geo, 8002)
  → код вызывает MCP: "Berlin"      → возвращается в LLM
  → LLM                             → tool_calls: get_weather({"city": "Berlin"})  (weather, 8003)
  → код вызывает MCP: JSON погоды   → возвращается в LLM
  → LLM: «В Берлине сейчас 15.2°C, ветер 11.9 км/ч, влажность 82%»
```

Маршрутизация — та же, что и для reminder/news: LLM видит инструменты
всех серверов одним списком, а код по имени инструмента отправляет
вызов на его сервер (`_tool_routes`, `max_tool_rounds` = 5 — достаточно
на цепочку из двух звеньев). В правила инструментов в system-промпте
добавлен сценарий «какая погода»: `get_user_city` → `get_weather(city)`.
Если geo-сервер вернул `"Unknown"` или weather — `{"error"}`, LLM
сообщает об этом и не прерывает ход диалога.

### Панель MCP: список серверов и их инструментов

Кнопка «🔄 Обновить» панели опрашивает **все** серверы — stdio (Git) и
HTTP (напоминания, news, geo, weather) — и рисует инструменты группами:
заголовок «● geo», под ним карточки его инструментов. Сервер, не
ответивший на tools/list, не скрывает остальные: его группа помечается
красным с текстом ошибки (в статусе — «Подключён | N инструментов ·
нет связи: …»). Кнопка «▶ Вызвать» у инструмента отправляет вызов на
сервер этой группы (HTTP — `MCPRemoteCallWorker`), форма параметров
строится по inputSchema.

### Автозапуск MCP-серверов и скорость старта

При старте Flet-версии `launch_mcp_servers` (app/main.py) поднимает все
локальные MCP-серверы (напоминания 8000, новости 8001, гео 8002,

### RAG-пайплайн (`app/rag/`)

Пять режимов (`app/rag/pipeline.py`):

| Режим | Пайплайн |
|-------|----------|
| `basic` | question → embed → search(top_k) → LLM |
| `rewrite` | question → LLM rewrite → embed → search(top_k) → LLM |
| `rewrite_filter` | rewrite → search(top_k) → filter(threshold) → LLM |
| `reranker` | search(top_k) → rerank → top_k_final → LLM |
| `rewrite_reranker` | rewrite → search(top_k) → rerank → top_k_final → LLM |

Косинусная мера Chroma конвертируется в similarity: `score = 1 − distance`.

```
Вопрос → [Query Rewrite] → embed_query (Ollama, префикс search_query:)
       → Chroma.search(top_k) → [filter(threshold)] → [rerank → top_k_final]
       → промпт «Контекст: … Вопрос: …» → LLM → Ответ + источники
```

Путь с цитатами (`app/rag/citations.py`, вкладка «RAG-режимы» и
`RAGChatAgent.answer_with_citations`):

```
поиск чанков → avg(score) < 0.6 ? → да: «Не знаю» (LLM не вызывается)
             → нет: JSON mode (response_format=json_object, temp 0.2)
             → {"answer", "sources", "quotes"} → validate_quotes
               (цитата дословно есть в своём чанке? valid: True/False)
             → ответ + источники (флаг cited) + цитаты + «Проверка»
```

- **citations** — промпт JSON-режима (контекст с шапками
  `[chunk_id=N | source | section]`), `CitationAnswerer`
  (`response_format={"type": "json_object"}`, mock-режим собирает
  валидный JSON из чанков), `parse_citation_json` (переживает
  ```-ограждения и прозу вокруг JSON), `validate_quotes` (неверная
  цитата помечается `valid: False`, не выбрасывается), `should_abstain`
  (порог 0.6 откалиброван для nomic-embed-text), ответ модели без
  цитат ретраится один раз, `CitationError` деградирует ход к ответу
  с источниками без цитат.

- **chunkers** — две стратегии: `fixed`
  (RecursiveCharacterTextSplitter, 500/50) и `structure`
  (MarkdownHeaderTextSplitter по #/##/### + рекурсивный догон до
  chunk_size); метаданные чанков: `source, title, section, chunk_id,
  strategy, chunk_size, overlap` — не теряются на пути в Chroma.
- **embedder** — `POST /api/embed` локальной Ollama, модель
  `nomic-embed-text`, обязательные префиксы задач
  (`search_document:` / `search_query:`); sync + async, ошибки
  оборачиваются в человекочитаемый `EmbedderError`.
- **vector_store** — `chromadb.PersistentClient` (данные в
  `app/data/chroma_db/` переживают перезапуск), пространство
  **cosine**, коллекция `knowledge_base`; переиндексация очищает
  коллекцию (IDs `chunk_0..N` остаются уникальными).
- **retriever** — топ-K, сборка промпта (формат ТЗ: «Ответь на вопрос,
  используя только предоставленный контекст. Если в контексте нет
  ответа — скажи об этом»), форматирование источников.
- **indexer** — оркестрация: пошагово для UI (файл за файлом →
  прогресс-бар, эмбеддинг батчем в commit) и `index_directory` целиком
  для тестов/консоли.
- **rewriter** — `QueryRewriter`: переформулировка вопроса через
  DeepSeek API (temperature 0.3, тот же OpenAI-совместимый SDK);
  ошибка сети/пустой ответ не ломают ход — поиск идёт по исходному
  вопросу (`rewrite_error` в диагностике); в mock-режиме сеть не
  используется.
- **reranker** — fallback-цепочка `FallbackReranker`:
  `OllamaReranker` (кастомная сборка `xitao/bge-reranker-v2-m3` —
  стандартная Ollama реранкеры не поддерживает, любая ошибка →
  `RerankerError`) → `FlagEmbeddingReranker` (официальный пакет
  FlagEmbedding, `BAAI/bge-reranker-v2-m3`, use_fp16; пакет
  опционален) → `LexicalReranker` (пересечение токенов, без
  зависимостей). Первый заработавший бэкенд «залипает», его имя видно
  в UI; полный отказ реранка деградирует режим к топ-K эмбеддинга.
- **pipeline** — `RAGPipeline.retrieve(question, mode, top_k,
  top_k_final, threshold)`: собирает ступени по режиму и возвращает
  чанки, метаданные, similarity-скоры и диагностику (`search_query`,
  `rewrite_used`, `rerank_backend`, ошибки ступеней).

### Интеграция с ядром

`app/agent.py` (`RAGChatAgent`) — обёртка над ядром: режимы
переключаются на лету (`set_rag_enabled` / `set_top_k`), все сетевые
вызовы — `asyncio.to_thread` внутри async-обработчиков
(`page.run_task`), UI обновляется только из event loop Flet
(фоновые потоки UI не трогают). В ядре `src/agent.py` добавлен
одноразовый хук `set_rag_context(user_content, sources)`: контекст
подставляется **только в копию запроса к API** (последнее
user-сообщение), история диалога хранит вопрос как есть; после хода
контекст сбрасывается, источники возвращаются в `result["sources"]`.
Недоступная Ollama или пустая база **не ломают диалог**: вопрос уходит
без контекста, причина — в `result["rag_error"]` (предупреждение в UI).

## Известные ограничения

- Модели в списке заданы константой `AVAILABLE_MODELS` (`src/utils.py`) —
  добавьте свою в список, если понадобится.
- Приложение рассчитано на интерактивную графическую сессию
  (не запускается «вслепую» без дисплея).
- **Долговременная память — отдельный файл** `data/long_memory.db`; она не
  удаляется вместе с БД чата и очищается только явно. Предложения LLM (pending)
  хранятся в той же БД.
- **Служебный запрос классификации памяти** (маркер `[[КЛАССИФИКАЦИЯ_ПАМЯТИ]]`)
  — это +1 запрос к API за ход при `MEMORY_PROPOSE_LLM=true`; его токены и
  стоимость считаются отдельными счётчиками `memory_*`.
- **Закрепления привязаны к сообщениям активной ветки**: при переключении ветки
  пины сбрасываются (индексы сообщений у веток свои).
- Рабочая память **своя у каждой ветки**, долговременная — **общая** для всех
  веток и сессий.
- **Панель MCP и сервер напоминаний — разные подсистемы**: панель
  работает со stdio-сервером (`MCP_SERVER_COMMAND`, по умолчанию
  open-internet-mcp), напоминания — с HTTP-сервером
  `reminder_server.py`. Первый запуск `npx open-internet-mcp`
  скачивает пакет (нужен интернет и Node.js) и может превысить таймаут —
  достаточно нажать «Обновить» ещё раз.
- **Серверы напоминаний и новостей живут 24/7**: окна консолей
  закрываются вручную (или Ctrl+C); при повторном запуске приложения
  серверы подхватываются, а не дублируются. Порт занят другим
  процессом — индикатор напоминаний покажет «сервер не запущен».
- **RSS-ленты внешние**: при недоступности всех лент `search_news`
  вернёт `{"error": ...}` и LLM сообщит об этом; ленты настраиваются
  через `NEWS_RSS_FEEDS`.
- При закрытии приложения во время загрузки списка процесс сервера
  завершается best-effort (воркер daemon-поток; активная сессия
  разрывается при выходе).
