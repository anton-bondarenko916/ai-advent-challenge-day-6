# ПРОМПТ ДЛЯ CODE ASSISTANT: ЯВНАЯ МОДЕЛЬ ПАМЯТИ АГЕНТА (MEMORY LAYERS) + КНОПКИ СОХРАНЕНИЯ У СООБЩЕНИЙ

## ЦЕЛЬ ЗАДАЧИ
Доработать приложение **DeepSeek Chat** (Python 3.9+ / Tkinter / DeepSeek API;
SQLite-персистентность, подсчёт токенов, стратегии контекста, ветки диалога) —
дать агенту **явную модель памяти из трёх слоёв** и управление ею из интерфейса:

1. **Краткосрочная (`short_term`)** — текущий диалог: буфер сообщений активной ветки;
2. **Рабочая (`working`)** — данные текущей задачи: цель, статус, план, ограничения,
   решения, открытые вопросы, артефакты;
3. **Долговременная (`long_term`)** — профиль пользователя, принятые решения,
   знания; переживает перезапуск, очистку истории, удаление ветки и удаление БД чата.

Обязательные свойства доработки:

- **разные типы памяти хранятся отдельно** — разные таблицы/файлы, разное время
  жизни, разные владельцы (ветка vs. глобально), разные API;
- **явный выбор, что и куда сохраняется** — единственная точка записи, никаких
  «тихих» автосохранений; модель может только **предлагать**, решает пользователь;
- **рядом с каждым сообщением в UI есть кнопки**, сохраняющие информацию об этом
  сообщении в выбранный слой (в краткосрочную / в рабочую / в долговременную);
- **проверяемость** — видно, какие данные попали в каждый слой, сколько они стоят
  в токенах и как именно они меняют контекст запроса и ответы агента.

Изменять существующие файлы **на месте** (не переписывать проект с нуля). Сохранить
весь текущий функционал: персистентность, токены/цены, стратегии контекста,
ветки, mock-режим, «ошибка API → откат сообщения → Повторить», надёжное поле ввода.
Проверить в конце: **все существующие 217 тестов зелёные** + новые.

  обратносовместимо;

  «не изменять сохранённое», `{}` — «явно стереть»; миграции схемы идемпотентны и
  при сбое не роняют приложение (лог + работа как раньше);

## РЕШЕНИЯ, СОГЛАСОВАННЫЕ С ЗАКАЗЧИКОМ (реализовать именно так)
1. **Слоёв ровно три**, имена в коде — `short_term`, `working`, `long_term`
   (в UI — «Краткосрочная (диалог)», «Рабочая (задача)», «Долговременная (профиль,
   решения, знания)»). Слой передаётся строкой и валидируется; неизвестный слой —
   ошибка, а не «положим куда-нибудь».
2. **Краткосрочная память** — это сообщения активной ветки (уже есть) плюс
   механизм **закрепления (pin)**: «сохранить в краткосрочную» = закрепить
   сообщение, чтобы оно **всегда** уходило в запрос, даже когда вышло за окно
   `WINDOW_KEEP_LAST_N`. Закреплённых не больше `MEMORY_PIN_MAX` (5); при
   превышении вытесняется самое старое закрепление с WARNING в лог.
3. **Рабочая память** — структурированное состояние задачи
   (`goal`, `status`, `plan[]`, `constraints[]`, `open_questions[]`) плюс элементы
   `key → value` с видом (`decision` / `artifact` / `note`). Она **привязана к
   ветке** (у каждой ветки своя), переключается вместе с веткой и стирается
   кнопкой «Новая задача» / «Очистить рабочую память» / удалением ветки.
   Ключи→значения рабочей памяти — **те же объекты**, что `FactsStore`
   (не второй параллельный словарь): для стратегии `sticky_facts` они уходят
   в запрос уже существующим блоком фактов, и рабочая память **не дублирует их
   в своём блоке** (это проверяется тестом на отсутствие дублей).
4. **Долговременная память** — **глобальная** (не привязана к ветке) и живёт в
   **отдельном файле SQLite** (`data/long_memory.db`), поэтому переживает
   «Очистить историю», удаление ветки и удаление `data/chat_history.db`.
   Разделы: `profile` (имя, язык, роль, устойчивые предпочтения), `decisions`
   (принятые решения и договорённости), `knowledge` (устойчивые знания, правила,
   ссылки). Пишется **только явно** (кнопка/окно/команда) либо подтверждённым
   предложением. Удаляется только явным «Забыть» / «Очистить раздел» /
   «Очистить долговременную».
5. **Единственная точка записи — `MemoryManager.route(...)`** (см. п. 1 модуля
   `src/memory.py`). Через неё проходят: кнопки у сообщений, окно «Память…»,
   текстовые команды, подтверждение предложений LLM. Никакой код не пишет в слои
   в обход роутера.
6. **LLM только предлагает, пользователь решает.** После хода (если включено
   `MEMORY_PROPOSE_LLM`) выполняется **один** служебный запрос с маркером
   `MEMORY_MARKER = "[[КЛАССИФИКАЦИЯ_ПАМЯТИ]]"`, возвращающий строгий JSON с
   кандидатами по слоям и `confidence`. Кандидаты кладутся в **pending** и в слои
   **не попадают**; пользователь принимает (выбирая слой) или отклоняет их в окне
   «Память…». `MEMORY_AUTO_APPLY` существует, по умолчанию **false**, и в README
   прямо сказано, что его включение нарушает принцип явного выбора.
7. **Порядок блоков памяти в запросе фиксирован и проверяется тестом**
   (см. «Состав запроса»). Блоки памяти — это `system`-сообщения, поэтому
   `_limit_context()` их не вытесняет; бюджет `MEMORY_MAX_TOKENS` ограничивает
   их сверху с приоритетным усечением и WARNING в лог.
8. **UI:** у каждого сообщения — три кнопки сохранения по слоям; отдельное окно
   «Память…» с тремя вкладками и предпросмотром «Что уходит в запрос»; блок
   «Токены» и статус-бар показывают память (сколько элементов и токенов в каждом
   слое). Всё, что ходит в API по кнопкам, — в фоновом потоке через `_run_action()`.
9. **mock-режим остаётся изолированным:** сохранение в память работает только
   «в процессе» (в памяти) и **ничего не пишет и не читает** из БД; в статус-баре
   честное «mock: сохранено только в памяти процесса».
10. **`MEMORY_ENABLED=false`** (или отсутствие `memory_settings`) → поведение
    приложения **ровно как сейчас**, все 217 существующих тестов зелёные.

| Слой | Что хранит | Где хранится | Область | Кто пишет | Когда исчезает | Что уходит в запрос |
|---|---|---|---|---|---|---|
| **short_term** | сообщения диалога + пометки «закреплено» | таблица `messages` БД чата (колонки `pinned`, `pin_note`) | активная ветка | автоматически каждый ход + вручную (кнопка «В диалог») | «Очистить историю», удаление ветки, открепление | последние `WINDOW_KEEP_LAST_N` сообщений + все закреплённые (в хронологическом порядке) |

| **pending** | предложения классификации от LLM | БД долговременной памяти, таблица `pending_memory` | глобально | служебный LLM-запрос после хода | принятие/отклонение, «Очистить предложения» | **не уходит** до подтверждения |

Правило-мнемоника (в README дословно): *«диалог забывается окном, задача —
её закрытием, долговременная память — только явным “Забыть”»*.

## ТРЕБОВАНИЯ К РЕАЛИЗАЦИИ

### 1. Новый модуль `src/memory.py`
Модуль **не импортирует tkinter**; вся логика тестируется без GUI. Ошибки хранилища
не пробрасываются наружу (лог + `error` в результате), как в `ContextStore`.

- **Константы слоёв**: `SHORT_TERM = "short_term"`, `WORKING = "working"`,
  `LONG_TERM = "long_term"`; `LAYERS = (SHORT_TERM, WORKING, LONG_TERM)`;
  `LAYER_TITLES` (русские подписи для UI и блоков запроса); разделы долговременной:
  `SECTIONS = ("profile", "decisions", "knowledge")`; `normalize_layer(name)` —
  понимает русские подписи кнопок и бросает понятную ошибку (например,
  `MemoryError` собственный или `ValueError`, но **не** тихий fallback).
- **`WorkingMemory`**: поля task + `items`; `set_field(name, value)`,
  `drop_field(name)`, `remember(key, value, kind)`, `forget(key)`, `clear()`,
  `as_dict()`/`from_dict(raw)` (устойчиво к мусору: битый JSON → пустая память +
  WARNING), `token_count(counter)`, `to_text(counter, max_tokens)` — текст блока
  памяти с приоритетным усечением (сначала `plan`, затем `open_questions`, затем
  `artifacts`, `constraints` — goal/status никогда не вытесняются).
- **`LongTermStore`**: собственный файл SQLite (`db_path`), собственный
  `SCHEMA_VERSION = "1"` в своей таблице `meta`, короткоживущее соединение на
  операцию (тот же паттерн, что `ContextStore._session()`), файл создаётся **лениво**
  и **не создаётся в mock-режиме**. API: `exists`, `load()`, `add(section, key,
  value, source, source_message)`, `update`, `forget(section, key)`,
  `clear_section(section)`, `clear_all()`, `list_items(section=None)`, `search(query)`,
  `mark_used(section, key)`, `as_dict()`, `to_text(counter, max_tokens)`,
  `token_count(counter)`, `export_markdown(path)`, `import_markdown(path)`,
  `close()`. `UNIQUE(section, key)`; новое значение перезаписывает старое
  (`updated_at`, `source`), но **не** молча меняет раздел.
- **`PendingMemoryStore`** (можно внутри `LongTermStore` или отдельным классом над
  тем же файлом): `add(items, source_message)`, `list()`, `get(id)`,
  `accept(id, layer)`, `reject(id)`, `clear()`. Дедупликация по
  `(section|layer, key, value)`.
- **`MemoryClassifier`**:
  - `classify_local(text)` → предложения по слоям **локальными правилами**
    (переиспользовать/расширить `facts.extract_local`, добавить маркеры
    «навсегда/всегда/запомни в долговременную» → `long_term`,
    «по этой задаче/для задачи/план/дедлайн» → `working`,
    «запомни на этот диалог/учти в диалоге» → `short_term`);
  - `MEMORY_MARKER = "[[КЛАССИФИКАЦИЯ_ПАМЯТИ]]"`, `DEFAULT_MEMORY_PROMPT` — шаблон
    инструкции, требующий **строго JSON**:
    `{"short_term": [{"text": "...", "confidence": 0.0..1.0}],
      "working": [{"key": "...", "value": "...", "kind": "decision|artifact|note",
                   "confidence": ...}],
      "long_term": [{"section": "profile|decisions|knowledge", "key": "...",
                     "value": "...", "confidence": ...}]}`;
    инструкция обязана требовать «не выдумывать факты, которых нет в тексте»;
  - `build_request(text, context_hint)` → dict для `_call_service_api`;
  - `parse(raw_text)` — вырезание JSON (в т.ч. из ```-блока), при мусоре —
    `{"error": ...}` и пустые списки (прежние данные не трогаются);
  - `classify(text, call_service, settings)` — LLM-предложение + локальные правила,
    фильтр `confidence >= MEMORY_MIN_CONFIDENCE`, лимит числа кандидатов.
- **`MemoryManager`** — единственный роутер и владелец слоёв:
  - `route(layer, text, *, key=None, section=None, kind=None, source="manual",
    message_index=None, branch_id=None) -> dict` — валидация слоя, нормализация
    ключа (пустой ключ → вывод из текста/автогенерация `заметка-N`), запись
    строго в свой слой, лог `INFO` с указанием слоя и источника, возврат
    `{"ok", "layer", "key", "value", "section", "error"}`;
  - `pin(message_index, note=None)` / `unpin(message_index)` / `toggle_pin(index)` /
    `list_pinned()`, лимит `MEMORY_PIN_MAX`;
  - `working_*` (task-поля, элементы, «Новая задача» с опциональным переносом
    выбранных решений в `long_term.decisions`);
  - `long_*` (добавить/изменить/забыть/очистить раздел/экспорт/импорт);
  - `pending_*` (список/принять с выбором слоя/отклонить/очистить);
  - `report() -> dict` — «какие данные в каком слое»: по каждому слою элементы,
    количество, токены, источник (`manual`/`confirmed`/`local`/`import`),
    `updated_at`, плюс `pending` и `budget`;
  - `build_blocks(counter, settings) -> List[Message]` — три `system`-сообщения
    (пустые слои не добавляются) в фиксированном порядке и с усечением по бюджету.

### 2. `src/storage.py` — схема v3 (БД чата)
- `SCHEMA_VERSION = "3"`; миграция **v2 → v3** идемпотентна и безопасна: к таблице
  `messages` добавляются `pinned INTEGER NOT NULL DEFAULT 0` и `pin_note TEXT`
  (по образцу `_upgrade_columns()`, storage.py:684 — каждая DDL в `try/except`,
  при сбое лог и работа как раньше, **без потери данных**); `_has_v2_schema`/
  `_ensure_schema` расширить так, чтобы «свежая» БД сразу создавалась в v3.
- `save_state(..., pinned=None, working=None)`: `pinned` — `Dict[int, Optional[str]]`
  (индекс сообщения диалога **без system** → заметка) или список индексов;
  `None` — не изменять/нули (обратная совместимость старых вызовов и тестов);
  `working` — `None` не изменять, `{}` явно стереть (та же семантика, что у
  `summary`/`facts`); рабочая память дополнительно дублируется в
  `meta['working_memory_<branch_id>']` (по образцу `_facts_key(branch_id)`).
- `load_state()` возвращает дополнительно `"pinned"` (список
  `{"index", "note"}`) и `"working_memory"` (dict|None).
- `clear()` очищает сообщения, параметры, статистику, конспект, факты, pinned и
  рабочую память **активной ветки**; **долговременную память не трогает** (другой
  файл — это осознанное свойство, зафиксировать комментарием и тестом).
- `BranchManager`/`switch`: рабочая память переключается вместе с веткой (как facts);
  создание ветки копирует рабочую память префикса; удаление ветки удаляет её копию.

### 3. `src/agent.py` — интеграция модели памяти
- **`__init__`**: новые параметры `memory_settings: Optional[Dict[str, Any]] = None`,
  `memory_manager=None`, `long_memory=None` (для тестов). В mock-режиме
  `LongTermStore` **не создаётся** (или создаётся с `enabled=False`) и не читается.
  `main.py:create_agent()` передаёт `memory_settings=get_memory_settings(config)`.
- **Состав запроса** — новый метод `_memory_blocks()` и вставка в
  `_build_context_messages()` (agent.py:550) **после** сборки стратегии/legacy-режима и
  **до** `_limit_context()`:
  ```
  1. system-промпт агента
  2. system: «ДОЛГОВРЕМЕННАЯ ПАМЯТЬ (профиль, решения, знания): …»   # если не пусто
  3. system: «РАБОЧАЯ ПАМЯТЬ (текущая задача): …»                    # если не пусто
  4. system: «ЗАКРЕПЛЁННЫЕ СООБЩЕНИЯ ДИАЛОГА: [индекс] роль: текст»  # если есть пины
  5. дальше — то, что вернула стратегия (system-промпт + факты + последние N)
  ```
  Инвариант: без `MEMORY_ENABLED` (или при пустых слоях) результат **побайтово**
  совпадает с текущим — это проверяется тестом «контекст не изменился».
  Блок рабочей памяти **не повторяет** пары, которые уже уходят блоком фактов
  `sticky_facts` (тест на отсутствие дублей).
- **`send_message()`**: после успешного хода, если `MEMORY_PROPOSE_LLM` и не mock,
  выполнить **один** служебный запрос классификации (через существующий
  `_call_service_api()`), положить кандидатов в pending, учесть его токены
  **отдельными** счётчиками `memory_requests`, `memory_prompt_tokens`,
  `memory_completion_tokens`, `memory_estimated_tokens`, `memory_cost_usd`
  (по образцу `_account_facts()`, agent.py:1696). Ошибка классификации **не ломает
  ход**: WARNING, `_memory_error`, повтор на следующем ходу.
- **Персист/восстановление**: `_persist()` передаёт `pinned` и `working`;
  `_load_context()` восстанавливает pinned (индексы вне диапазона — игнорировать с
  предупреждением) и рабочую память активной ветки; долговременная память читается
  при старте (если включена) независимо от того, есть ли история в БД чата.
  `close()` делает финальный flush и закрывает `LongTermStore`.
- **Публичное API** (все методы — под существующим `RLock`, ошибки не бросаются):
  - `save_to_memory(layer, text, *, key=None, section=None, kind=None,
    source="manual", message_index=None) -> dict`;
  - `pin_message(index, note=None)`, `unpin_message(index)`, `list_pinned()`;
  - `get_working_memory()`, `set_task_field(field, value)`,
    `add_working_item(key, value, kind)`, `clear_working_memory()`,
    `start_new_task(carry_to_long=None) -> dict`;
  - `get_long_memory(section=None)`, `remember_forever(section, key, value)`,
    `forget_forever(section, key)`, `clear_long_memory(section=None)`,
    `export_long_memory(path=None)`, `import_long_memory(path=None)`;
  - `classify_message(index) -> dict` — предложения по одному сообщению
    (локальные правила всегда; LLM — если включено и не mock) для предзаполнения
    диалога сохранения;
  - `get_pending_memory()`, `accept_pending(pending_id, layer=None)`,
    `reject_pending(pending_id)`, `clear_pending_memory()`;
  - `get_memory_report() -> dict` — `MemoryManager.report()` + `budget` + `pending`;
  - `preview_context() -> List[dict]` — реальный список сообщений будущего запроса
    с пометкой слоя (`{"layer", "role", "content", "tokens"}`, слой для
    диагностики: `system`, `long_term`, `working`, `pinned`, `short_term`);
  - `clear_memory(layer) -> dict` — явная очистка слоя (для `long_term` — раздел/всё,
    для `short_term` — сообщения ветки/пины, для `working` — рабочая память);
  - `get_memory_settings() -> dict` (по образцу `strategy_settings()`).
- **`get_token_stats()`** расширить обратносовместимо: блок `memory`:
  `{enabled, short_term:{messages, pinned, tokens}, working:{items, tokens},
  long_term:{items, sections, tokens}, pending, total_tokens, budget, truncated,
  error}`; в `context` добавить `memory_tokens`; в `session` — счётчики `memory_*`.
- **`clear_history()`** очищает сообщения **активной ветки** (краткосрочную),
  пины этой ветки и её рабочую память; **долговременную не трогает** — в окне
  подтверждения явно написать, что «долговременная память сохранится».
- Потокобезопасность: всё под `RLock`; служебные запросы — только через
  `_call_service_api()` (подменяемо в тестах и sim-режиме бенчмарка).

## КРИТЕРИИ ПРИЁМКИ
- [ ] В агенте есть три слоя памяти с явной семантикой, и каждый хранится отдельно:
      краткосрочная — сообщения ветки (+`pinned`) в БД чата; рабочая — `meta`-ключи
      ветки; долговременная — **отдельный файл** `data/long_memory.db`.
- [ ] Запись возможна только явно и только через единый роутер `MemoryManager.route`;
      неизвестный слой — ошибка, а не тихая запись «куда попало».
- [ ] Рядом с **каждым** сообщением в UI есть кнопки сохранения в краткосрочную,
      рабочую и долговременную память (плюс дубли в контекстном меню правого клика);
      состояние (`✓`/`📌`) восстанавливается из агента после перерисовки и перезапуска.
- [ ] LLM-классификация только **предлагает** (pending); принятие/отклонение —
      вручную; `MEMORY_AUTO_APPLY=false` по умолчанию; служебный запрос помечен
      `[[КЛАССИФИКАЦИЯ_ПАМЯТИ]]` и учитывается отдельными счётчиками.
- [ ] Порядок блоков в запросе: system → долговременная → рабочая → закреплённые
      сообщения → окно стратегии; пустые слои не добавляются; бюджет
      `MEMORY_MAX_TOKENS` соблюдается; `_limit_context()` не вытесняет блоки памяти.
- [ ] Закреплённое сообщение уходит в запрос даже за пределами окна; незакреплённое
      вытесняется — это подтверждено тестом и прогоном бенчмарка.
- [ ] `clear_history()` / «Очистить историю» удаляет только краткосрочную (ветку) и
      её рабочую память; долговременная память сохраняется (проверено тестом).
- [ ] Рабочая память привязана к ветке (своя у каждой) и восстанавливается после
      перезапуска; долговременная — общая для всех веток и сессий.
- [ ] Окно «Память…»: три вкладки + pending + сводка токенов по слоям + кнопка
      «Что уходит в запрос» (`preview_context()`); UI не «зависает» (фон + очередь).
- [ ] Mock-режим изолирован: `chat_history.db`/`long_memory.db` не создаются, память
      только в процессе.
- [ ] `MEMORY_ENABLED=false` возвращает поведение, идентичное текущему (тест на
      неизменность контекста).
- [ ] Миграция схемы v2 → v3 без потери данных; старые БД читаются.
- [ ] Все 217 существующих тестов + новые — зелёные, офлайн, без новых зависимостей.
- [ ] README и `.env.example` описывают модель слоёв, кнопки и переменные.

## ЧТО НЕ ДЕЛАТЬ
- Не добавлять зависимости (только stdlib + уже используемые `openai`,
  `python-dotenv`, `tiktoken`).
- Не делать автосохранение в слои по умолчанию и не включать `MEMORY_AUTO_APPLY`:
  явный выбор — суть задачи.
- Не удалять долговременную память при очистке истории, смене системного промпта,
  смене стратегии, удалении ветки или удалении БД чата.
- Не дублировать факты `sticky_facts` в блоке рабочей памяти и не заводить второй
  параллельный словарь фактов (рабочая память использует существующий `FactsStore`).
- Не ломать обратную совместимость публичных API (`send_message`, `get_token_stats`,
  `save_state`/`load_state`, `remember`/`forget`/`clear_facts`, ветки) — только

- Не выполнять сетевые вызовы в тестах (подменять `_call_api`/`_call_service_api`);
  не хардкодить цены; не трогать mock-изоляцию и «ошибка API → откат → Повторить».
- Не блокировать UI: сохранение/классификация/экспорт — в фоне через `_run_action()`;
  не создавать второй `Tk()`; не держать ссылки на виджеты, уничтоженные при
  перерисовке чата.
- Не менять формат сообщений `{role, content}` (метаданные слоёв — отдельно от
  `_message_history`).

## ОГРАНИЧЕНИЯ СРЕДЫ РАЗРАБОТКИ (учесть!)
- **Нет доступа к PyPI и нет сети из кода**: пакеты не устанавливаются; тесты
  офлайн; ручная проверка с реальным ключом — только у пользователя.
- Windows + песочница: системный TEMP и удаление каталогов могут быть недоступны —
  все тестовые файлы создавать внутри репозитория (`tests/tmp_memory/`, шаблон
  `tests/tmp*/` уже в `.gitignore`) и не полагаться на очистку каталогов.
- Tk в одном процессе доставляет клавиатурные события только первому окну —
  GUI-тесты обязаны использовать общий root из `tests/gui_helpers.py` и вызывать
  обработчики напрямую, а не полагаться на синтетические клики по встроенным кнопкам.
- Консоль может искажать кириллицу — это не ошибка приложения.
- Доступны Python 3.13 и установленный `openai` 3.6.0.
