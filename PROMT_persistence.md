## ЦЕЛЬ ЗАДАЧИ
Доработать существующее десктопное приложение **DeepSeek Chat** (Python 3.9+ / Tkinter /
DeepSeek API), написанное ранее по приложенному проекту, — добавить агенту **сохранение
контекста между запусками**:

- история диалога (messages) и параметры агента хранятся в **SQLite**;
- при перезапуске агент **загружает** сохранённые историю и параметры обратно;
- диалог продолжается так, как будто агент не выключался.

Изменять существующие файлы **на месте** (не переписывать проект с нуля). Сохранить весь
текущий функционал и обратную совместимость (все существующие тесты должны остаться зелёными).

Ключевые факты текущего поведения (обязательно учесть):
- `DeepSeekAgent.__init__(api_key, model=None, system_prompt=None, temperature=None,
  max_tokens=None, mock_mode=False, max_history_messages=50)`; приватные `_message_history`
  (первый элемент — system), `_client`, `_lock` (RLock); валидация через `src.utils`;
  `send_message()` возвращает dict `{text, model, tokens, response_time, finish_reason, error, timestamp}`
  и **не бросает исключений**; при ошибке API сообщение пользователя **откатывается**
  (`_rollback_user_message`); после успеха история урезается `_trim_history()` до
  `max_history_messages` (по умолчанию 50) сообщений, не считая system;
- `update_config(**kwargs)` поддерживает model/system_prompt/temperature/max_tokens/mock_mode/
  max_history_messages; **смена system_prompt сбрасывает историю** (`_init_history`);
- `clear_history()` сбрасывает историю до одного system-сообщения;
- в `mock_mode=True` агент не создаёт HTTP-клиента и отвечает заглушками;
- UI перерисовывает чат из `agent.history` (это источник истины), на старте
  `_apply_config_to_controls()` синхронизирует виджеты со значениями агента;
- запросы выполняются в `threading.Thread` (по потоку на запрос), результат — через
  `queue.Queue` + `root.after`; `_on_close()` вызывает `root.destroy()`.

## ТРЕБОВАНИЯ К РЕАЛИЗАЦИИ

### 1. Новый модуль `src/storage.py`
Класс хранилища (имя на усмотрение, например `ContextStore`) поверх `sqlite3` из stdlib.

- Конструктор принимает путь к БД; каталог создаётся при необходимости; соединение
  настраивается; создаются таблицы (если отсутствуют), например:
  - `meta(key TEXT PRIMARY KEY, value TEXT)` — параметры агента и `schema_version`;
  - `messages(id INTEGER PRIMARY KEY AUTOINCREMENT, role TEXT NOT NULL, content TEXT NOT NULL,
    created_at TEXT NOT NULL)` — сообщения в порядке `id`;
- Методы (точные сигнатуры — на усмотрение, но обязанности такие):
  - загрузка состояния: возвращает `{"messages": [...], "params": {...}}` либо `None`,
    если БД/файла нет или диалог пуст; порядок сообщений сохраняется;
  - сохранение диалога целиком: **полная перезапись** таблицы `messages` из переданного
    списка (≤ 50–60 строк — дёшево и исключает рассинхрон с `_trim_history`) + запись
    параметров в `meta` — в одной транзакции;
  - сохранение только параметров (`save_params`);
  - `clear()` — очищает сообщения и параметры (кроме `schema_version`);
  - `close()` — закрывает соединение (идемпотентно);
- **Потокобезопасность (критично):** запросы выполняются в отдельных потоках, а соединение
  `sqlite3` по умолчанию не переживает смену потока. Решение на выбор: (а) короткоживущее
  соединение на каждую операцию, либо (б) одно соединение с `check_same_thread=False`,
  используемое **только из-под RLock агента**. Описать выбранный вариант в комментарии.
  Все обращения к хранилищу должны выполняться внутри той же блокировки, что и мутация
  истории агента.
- Ошибки БД (`sqlite3.Error`) не должны ронять приложение и запрос: логировать через
  `utils.get_logger` и продолжать работу в памяти (агент функционирует без персиста).
- Файл БД **создавать лениво** — при первом реальном сохранении. Загрузка при отсутствии
  файла должна просто вернуть «пусто», не создавая файл.
- В `meta` хранить `schema_version`; при несовпадении со схемой приложения — не читать
  чужие/старые данные (залогировать и начать с пустого состояния).

### 2. `src/agent.py` — интеграция персиста в `DeepSeekAgent`
- Новые параметры `__init__`: `storage_path: Optional[str] = None` (по умолчанию из
  конфигурации, см. п. 4) и/или готовый объект хранилища; флаг включения. В `mock_mode`
  хранилище **не используется вовсе** (ни чтение, ни запись).
- **Загрузка при старте:** после `_init_history()`, если хранилище включено и файл БД
  существует: прочитать состояние; **только если история пуста** (один system) — применить:
  1) восстановить `system_prompt` из параметров и пересоздать system-сообщение истории
     (`_init_history` с восстановленным промптом), 2) восстановить `model`, `temperature`,
     `max_tokens`, прогнав значения через валидаторы `src.utils`; если сохранённое значение
     невалидно — оставить значение по умолчанию/из `.env` и залогировать предупреждение
     (не ронять запуск), 3) загрузить сохранённые сообщения в `_message_history` (после
     system) и применить `_trim_history()`.
- **Сохранение:** в `send_message()` после успешного добавления ответа ассистента и
  `_trim_history()` — сохранить историю и текущие параметры. При ошибке API (откат
  сообщения) сохранять не нужно — на диске уже согласованное состояние.
- `update_config(...)`: при смене `system_prompt` — после `_init_history()` очистить
  хранилище и записать новый промпт; при смене `model/temperature/max_tokens` — применить
  в памяти и вызвать сохранение параметров (чтобы после рестарта параметры совпадали).
  В mock-режиме всё это игнорируется.
- `clear_history()`: после сброса в памяти — очистить и хранилище.
- Новый метод `close()`: финальный flush (сохранение текущего состояния, если оно ещё не
  сохранено) + `close()` хранилища; идемпотентный и безопасный при повторном вызове.
- Обратная совместимость: все существующие вызовы/тесты (без хранилища или в mock-режиме)
  должны работать без изменений. Существующие 27 тестов не редактировать без необходимости.

### 3. `main.py` и `src/ui.py`
- `main.py`: собрать хранилище из конфигурации (`STORAGE_ENABLED`, `STORAGE_PATH`) и
  передать в `DeepSeekAgent`; после завершения `mainloop` (и в `finally`) гарантированно
  вызвать `agent.close()`.
- `src/ui.py`: в `_on_close()` перед `root.destroy()` вызывать `agent.close()`.
  Дополнительно (важно для проверки «на практике»): при старте, если агент загрузил
  сохранённый контекст (в истории больше одного сообщения), показать в статус-баре
  сообщение вида `Контекст восстановлен: N сообщений · модель X`. Убедиться, что
  `_apply_config_to_controls()` исполняется **после** загрузки состояния агентом
  (текущий порядок в `ChatApplication.__init__` это гарантирует — проверить и
  прокомментировать).
- Кнопки «Очистить историю» и «Применить» уже идут через `agent.clear_history()` /
  `agent.update_config(system_prompt=...)` — отдельных правок UI не требуется, только
  тексты статуса при необходимости.
